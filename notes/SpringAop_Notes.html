11Spring AOP

Phase 2 said "Spring may hand you a proxy instead of the object you wrote" and Phase 3 said "the transaction opens at the AOP layer". This is where that claim gets cashed in — and where a whole family of silent Spring bugs stops being mysterious and starts being predictable.

11.1 Why AOP — cross-cutting concerns

Some responsibilities belong to no one class but must happen in many of them: logging, timing, auditing, security checks, retries, transactions, caching. OO decomposition has no home for them, so they get copy-pasted into every method that needs them.

// one line of business logic, twelve lines of everything else
public Order place(OrderRequest request) {
    long start = System.nanoTime();                            // timing
    log.info("place() called with {}", request);             // logging
    securityService.check("ORDER_WRITE");                      // security
    try {
        Order order = doPlace(request);                        // <- the actual work
        auditService.record("ORDER_PLACED", order.getId());    // auditing
        return order;
    } catch (Exception e) { log.error("place() failed", e); throw e; }
    finally { metrics.record("place", System.nanoTime() - start); }
}

Three problems that compound: duplication (change the log format, touch forty methods), obscured intent (reviewers hunt for the behaviour), inconsistency (someone forgets the audit call and nobody notices for months). AOP lets you declare the plumbing once, describe where it applies with an expression, and let the framework apply it.

You are already using it

@Transactional, @Cacheable, @Async, @Retryable, @PreAuthorize and @Validated are all Spring AOP. Once you understand the mechanism, "the annotation that silently does nothing" becomes one predictable cause with five symptoms.

11.2 The vocabulary

TermMeaning in Spring AOP
Join pointA point where advice could apply. In AspectJ this includes field access and constructors; in Spring AOP it is always a method execution on a Spring bean
PointcutAn expression selecting which join points: execution(* com.acme.service.*.*(..))
AdviceThe code that runs, and when: @Before, @After, @AfterReturning, @AfterThrowing, @Around
AspectA class combining pointcuts and advice, marked @Aspect
TargetThe real bean being advised — your OrderService
ProxyThe object Spring actually injects: same type as the target, wrapping it. Callers never see the target
WeavingLinking aspects to targets. Spring does this at runtime, by creating proxies during bean post-processing. AspectJ can weave at compile or load time
Spring AOP is not AspectJ

Spring AOP borrows AspectJ's annotations and pointcut syntax but uses its own runtime proxy mechanism. That is why it can only advise public method calls on Spring beans, made from outside the object. Full AspectJ weaves into the bytecode and can advise private methods, fields, constructors and non-Spring objects. Saying this precisely is a strong interview signal.

11.3 @Aspect and @EnableAspectJAutoProxy

<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-aop</artifactId></dependency>

@Aspect                       // marks it as an aspect
@Component                    // AND it must be a Spring bean - both are required
public class LoggingAspect {
    @Before("execution(* com.acme.service.*.*(..))")
    public void logEntry(JoinPoint jp) {
        log.debug("-> {}.{}", jp.getSignature().getDeclaringTypeName(), jp.getSignature().getName());
    }
}

spring.aop.auto=true                   # default
spring.aop.proxy-target-class=true     # default in Boot - always CGLIB, see 11.7
Both annotations, always

@Aspect alone does nothing — Spring never sees the class. @Component alone makes it a bean but not an aspect. Forgetting @Component is the most common reason a new aspect "does not fire", and it fails silently.

Under the hood

@EnableAspectJAutoProxy registers AnnotationAwareAspectJAutoProxyCreator, a BeanPostProcessor that inspects every bean at postProcessAfterInitialization and wraps the matching ones in a proxy. In Boot, AopAutoConfiguration switches it on when starter-aop is on the classpath. This is the Phase 2 mechanism: proxies are created at stage 8 of the bean lifecycle, after initialisation — which is exactly why @Transactional does not work inside @PostConstruct.

11.4 The five advice types

Nesting order for one aspect

@Around (before proceed()) → @Before → target method → @AfterReturning or @AfterThrowing → @After (finally, always) → @Around (after proceed()). @Around wraps everything and is the only advice that can suppress the call, change arguments or replace the return value.

@Aspect @Component
public class DemoAspect {
    @Pointcut("execution(* com.acme.service..*(..))")
    public void serviceMethods() { }                                    // a reusable, named pointcut

    @Before("serviceMethods()")                       public void before(JoinPoint jp) { }
    @AfterReturning(pointcut = "serviceMethods()", returning = "result")
    public void afterReturning(JoinPoint jp, Object result) { }
    @AfterThrowing(pointcut = "serviceMethods()", throwing = "ex")
    public void afterThrowing(JoinPoint jp, Exception ex) { }
    @After("serviceMethods()")                        public void after(JoinPoint jp) { }   // finally

    @Around("serviceMethods()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        // before
        try { Object result = pjp.proceed(); /* after returning */ return result; }   // <- calls the target
        catch (Throwable t) { /* after throwing */ throw t; }
        finally { /* after (finally) */ }
    }
}
AdviceRunsCan it…
@BeforeBefore the methodRead arguments. Cannot change them or stop the call — only throwing does that
@AfterReturningAfter normal returnRead the return value. Cannot replace it
@AfterThrowingAfter an exceptionRead the exception. Cannot swallow it — that needs @Around
@AfterAlways, like finallyClean up. Does not know whether it succeeded
@AroundWraps the callEverything. Change arguments, skip the call, replace the return value, swallow or translate exceptions, retry
Prefer the weakest advice that does the job

@Around can do anything, which also means it can silently break things — forget proceed() and the target never runs, returning null with no error. If you only need to read arguments, use @Before; the reader then knows behaviour cannot be altered.

    String action = audited.value();
    Object result = pjp.proceed();

    return result;

The annotation-driven pointcut is the one to reach for

execution(* com.acme.service..*(..)) silently stops matching the day someone renames a package — no error, just missing behaviour. @annotation(Audited) is explicit at the call site, survives refactoring, and makes the behaviour visible to whoever reads the method later. Package pointcuts are fine for genuinely blanket concerns like timing everything.

11.6 JoinPoint and ProceedingJoinPoint

@Around("@annotation(com.acme.Timed)")
public Object time(ProceedingJoinPoint pjp) throws Throwable {
    MethodSignature sig = (MethodSignature) pjp.getSignature();
    String clazz  = sig.getDeclaringType().getSimpleName();
    String method = sig.getName();
    Object[] args = pjp.getArgs();
    Object target = pjp.getTarget();          // the REAL bean
    Object proxy  = pjp.getThis();            // the proxy
    Method m      = sig.getMethod();          // for reading annotations reflectively
    long t0 = System.nanoTime();
    try { return pjp.proceed(); }             // or pjp.proceed(new Object[]{ modifiedArg })
    finally { log.info("{}.{} took {} ms", clazz, method, (System.nanoTime() - t0) / 1_000_000); }
}

Three mistakes that produce silent bugs

Forgetting proceed() — the target never runs and the method returns null. Calling it twice — the method executes twice, which on a payment is memorable. Declaring the return type as void — an @Around must return Object, or the real return value is thrown away.

The classic JDK-proxy failure

A bean implements an interface, so Spring creates a JDK proxy typed as the interface. Code that injects the concrete class then fails at startup with BeanNotOfRequiredTypeException, because the proxy is not an instance of your class. Boot avoids this by defaulting to CGLIB — which is why you rarely meet it now, and why older tutorials talk about it constantly.

What CGLIB cannot advise: final classes and methods (Kotlin classes are final by default — the all-open plugin exists for this); private methods (not visible to a subclass); static methods (not virtual); and calls from inside the object — that is 11.8. Since Spring 4.3 CGLIB uses Objenesis to instantiate without calling a constructor, so "needs a no-arg constructor" and "constructor runs twice" are obsolete warnings.

11.8 The self-invocation problem

The single most common Spring bug at mid level

It produces no error, no warning and no log line — the annotation simply does nothing. A proxy can only intercept calls that pass through it. this.inner() never leaves the object.

@Service
public class OrderService {
    public void processAll(List<Order> orders) {
        for (Order order : orders) processOne(order);      // <- plain Java call on `this`
    }
    @Transactional                                          // NEVER APPLIES when called from processAll()
    public void processOne(Order order) { repository.save(order); }
}

processAll() was entered through the proxy, so the proxy did its work for that method. Inside the target, processOne(order) compiles to this.processOne(order) — an ordinary virtual call on the raw instance. The proxy is not in the call path. The same applies identically to @Async (runs on the caller's thread), @Cacheable (never consults the cache), @Retryable, @PreAuthorize and scoped proxies. One mechanism, not five quirks.

FixAssessment
Move the method to another beanThe right answer. The call now crosses a proxy boundary. Usually also improves the design — the two methods had different responsibilities
Self-injection with @LazyInject the bean into itself and call self.processOne(). Works, honest, odd to read
AopContext.currentProxy()Needs exposeProxy = true, couples code to Spring AOP. Avoid
AspectJ load-time weavingNo proxy, so self-invocation works. A JVM agent and build complexity. Rarely worth it
// the fix that also improves the design
@Service public class OrderService {
    private final OrderProcessor processor;
    public void processAll(List<Order> orders) { orders.forEach(processor::processOne); }   // crosses the proxy
}
@Service public class OrderProcessor {
    @Transactional public void processOne(Order order) { repository.save(order); }
}

// self-injection, if you must keep them in one class
@Service public class OrderService {
    private final OrderService self;
    public OrderService(@Lazy OrderService self) { this.self = self; }
    public void processAll(List<Order> orders) { orders.forEach(self::processOne); }        // through the proxy
}
How to spot it in review

Any @Transactional, @Async or @Cacheable method that is only ever called from within the same class is dead configuration. Search for the method name: if every call site is in the same file, the annotation is doing nothing.

11.9 Aspect ordering

Lower @Order value = OUTER aspect

First in, last out. @Order(1) LoggingAspect wraps @Order(2) SecurityAspect wraps @Order(3) TransactionAspect wraps the target. Spring's default order for @Transactional is LOWEST_PRECEDENCE, which already puts it innermost.

ConcernShould beWhy
Logging / tracingOutermostRecords total elapsed time and sees exceptions from every inner aspect
SecurityEarlyReject unauthorised calls before doing any work or opening a transaction
RetryOutside the transactionEach attempt needs its own transaction. Retrying inside reuses a connection that may already be rollback-only
CachingOutside the transactionA cache hit should avoid opening a transaction at all
TransactionInnermostSo it covers only the business call
Ordering within one aspect is not guaranteed

@Order orders aspects. Two @Before advices in the same aspect matching the same method have undefined relative order. If order matters, split them into separate aspect classes.

11.10 Practical aspects

// timing and metrics
@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface Timed { String value() default ""; }

@Aspect @Component
public class TimingAspect {
    private final MeterRegistry registry;
    @Around("@annotation(timed)")
    public Object time(ProceedingJoinPoint pjp, Timed timed) throws Throwable {
        String name = timed.value().isBlank() ? pjp.getSignature().toShortString() : timed.value();
        Timer.Sample sample = Timer.start(registry);
        String outcome = "success";
        try { return pjp.proceed(); }
        catch (Throwable t) { outcome = "error"; throw t; }
        finally { sample.stop(registry.timer("method.duration", "method", name, "outcome", outcome)); }
    }
}

// auditing - record AFTER proceed(), so a rolled-back action is never recorded
@Around("@annotation(audited)")
public Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
    String actor = SecurityContextHolder.getContext().getAuthentication().getName();
    Object result = pjp.proceed();                                  // let it fail before recording
    auditRepository.save(new AuditEntry(actor, audited.value(), Instant.now(), MDC.get("traceId"), summarise(pjp.getArgs())));
    return result;
}

// retry - a teaching example, not a production component
@Around("@annotation(retryable)")
public Object retry(ProceedingJoinPoint pjp, Retryable retryable) throws Throwable {
    int attempts = 0;
    while (true) {
        try { return pjp.proceed(); }
        catch (TransientException e) {
            if (++attempts >= retryable.maxAttempts()) throw e;
            Thread.sleep(retryable.backoffMs() * (1L << (attempts - 1)));    // exponential
        }
    }
}
Use Spring Retry or Resilience4j instead of writing retry yourself

Real retry needs jitter (to avoid synchronised retry storms), a circuit breaker (so a dead upstream is not hammered), per-exception classification (do not retry a 400) and metrics. spring-retry gives @Retryable and @Recover; Resilience4j adds circuit breaking, bulkheads and rate limiting. Micrometer already ships @Timed too — check before writing your own.

What not to use AOP for

Core business logic — behaviour hidden in an aspect is invisible at the call site. Anything order-dependent across many aspects. Hot paths where a proxy call per invocation is measurable. Things a decorator does more clearly — AOP earns its keep when the concern is genuinely scattered across many unrelated classes.

12Async, scheduling & events

Work that should not block the request thread, work that runs on a clock, and work that happens because something else did. All three are proxies or ThreadLocal boundaries in disguise, so every AOP rule from section 11 applies.

12.1 @EnableAsync and @Async

Phase 3 ended on a constraint: one container thread per request, held for the whole request, and only about 200 of them. Anything slow the caller does not need to wait for should be moved off that thread. Synchronous: sendEmail() 800 ms + writeAudit() 300 ms → thread held 1.1 s, 200 threads = 180 req/s ceiling. With @Async: controller responds in ~5 ms, the work runs on taskExecutor-3.

@Configuration
@EnableAsync                                    // required - @Async does nothing without it
public class AsyncConfig { }

@Service
public class NotificationService {
    @Async
    public void sendWelcomeEmail(User user) { mailClient.send(user.email(), "Welcome"); }   // fire and forget

    @Async
    public CompletableFuture<Report> buildReport(Long id) {                                // result you can await
        return CompletableFuture.completedFuture(reportEngine.build(id));
    }
}
Return typeMeaning
voidFire and forget. Exceptions are swallowed unless you register an AsyncUncaughtExceptionHandler (12.3)
CompletableFuture<T>The modern choice. Composable; exceptions surface on join()/get()
Future<T>Legacy. Blocking get() only
Anything elseIgnored — the caller receives null immediately
@Async is a proxy, so all the AOP rules apply

Calling an @Async method from within the same class runs it on the caller's thread; a private or final method cannot be advised; calling it from @PostConstruct happens before the proxy exists. If "async is not async", check the call site first.

The default executor changed in Boot 3.2

Before, the default was SimpleAsyncTaskExecutor: a new thread per task, never pooled — a slow-motion resource leak under load. Boot now auto-configures a ThreadPoolTaskExecutor tunable with spring.task.execution.*. Either way, define your own for anything important.

12.2 CompletableFuture with Spring

The real value of async is not one background task but running several independent calls in parallel and combining them.

@Service
public class DashboardService {
    public DashboardResponse load(Long customerId) {
        CompletableFuture<List<Order>>   o = orders.findAsync(customerId);     // ~300 ms
        CompletableFuture<List<Invoice>> i = invoices.findAsync(customerId);   // ~250 ms
        CompletableFuture<Usage>         u = usage.findAsync(customerId);      // ~400 ms
        CompletableFuture.allOf(o, i, u).join();                              // ~400 ms total, not 950
        return new DashboardResponse(o.join(), i.join(), u.join());
    }
}

future.thenApply(order -> toDto(order))                  // transform
      .thenCompose(dto -> enrichAsync(dto))              // chain another async call
      .thenCombine(otherFuture, (a, b) -> merge(a, b))   // combine two
      .orTimeout(2, TimeUnit.SECONDS)                     // fail if too slow
      .exceptionally(ex -> DashboardResponse.empty())    // fall back
      .whenComplete((r, ex) -> log.info("done"));         // side effect either way
Exceptions are wrapped · the request context does not follow

Anything thrown inside a task surfaces from join() as a CompletionException with the real cause nested — unwrap with getCause() or your catch (BusinessException e) never matches. And async tasks run on a different thread, so ThreadLocal state is gone: the SLF4J MDC is empty (your correlation id from Phase 3 disappears), the SecurityContext is empty, no active transaction or request scope. Fix the first two with a TaskDecorator and DelegatingSecurityContextAsyncTaskExecutor.

12.3 Custom executors and thread pool tuning

@Configuration @EnableAsync
public class AsyncConfig implements AsyncConfigurer {
    @Bean("taskExecutor")                                     // this NAME is the @Async default
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(8);
        ex.setMaxPoolSize(32);
        ex.setQueueCapacity(200);
        ex.setKeepAliveSeconds(60);
        ex.setThreadNamePrefix("app-async-");                  // shows up in every stack trace
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setWaitForTasksToCompleteOnShutdown(true);
        ex.setAwaitTerminationSeconds(30);
        ex.setTaskDecorator(new ContextCopyingDecorator());
        ex.initialize();
        return ex;
    }
    @Override public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) -> log.error("async {} failed", method.getName(), ex);   // void methods
    }
}
Under the hood: how the pool grows — the queue fills BEFORE new threads are created

(1) Fewer than corePoolSize threads exist → a new thread is created, even if others are idle. (2) Core threads exist → the task is queued. (3) Queue is full → now new threads up to maxPoolSize. (4) Max reached and queue full → the rejection policy fires. (5) Idle non-core threads die after keepAliveSeconds.

The tuning mistake almost everyone makes

core=5, max=100, queue=10000 looks generous but means the pool never grows past 5. Tasks pile into the queue for hours; maxPoolSize is only consulted once the queue is full. If you want elasticity, keep the queue small — and never unbounded, which turns backpressure into an OutOfMemoryError.

SettingGuidance
corePoolSizeConcurrent tasks at steady state. IO-bound: can far exceed CPU count; CPU-bound: near it
maxPoolSizeThe ceiling. Only reachable once the queue is full
queueCapacityNever unbounded
RejectedExecutionHandlerAbortPolicy (default) throws; CallerRunsPolicy makes the submitter run the task — crude but effective backpressure
threadNamePrefixCosts nothing, pays for itself the first time you read a thread dump
ShutdownwaitForTasksToCompleteOnShutdown + timeout, so a rolling deploy does not kill in-flight work
// carrying context across the thread boundary
public class ContextCopyingDecorator implements TaskDecorator {
    @Override public Runnable decorate(Runnable runnable) {
        Map<String, String> mdc = MDC.getCopyOfContextMap();               // captured on the CALLER
        RequestAttributes attrs = RequestContextHolder.getRequestAttributes();
        return () -> {                                                      // runs on the WORKER
            try {
                if (mdc != null) MDC.setContextMap(mdc);
                if (attrs != null) RequestContextHolder.setRequestAttributes(attrs);
                runnable.run();
            } finally { MDC.clear(); RequestContextHolder.resetRequestAttributes(); }
        };
    }
}

Several pools, on purpose

One shared executor means a slow email provider can starve report generation. Declare separate named executors and select one per method with @Async("emailExecutor"). This is the bulkhead pattern inside a single process — in fintech, the payment-gateway pool and the notification pool must never share threads.

12.4 @EnableScheduling and @Scheduled

@Configuration @EnableScheduling public class SchedulingConfig { }

@Component
public class ReportJobs {
    @Scheduled(fixedDelay = 60_000)                                  // 60 s after the previous FINISH
    public void pollQueue() { }
    @Scheduled(fixedRate = 30_000, initialDelay = 10_000)             // every 30 s from each START
    public void heartbeat() { }
    @Scheduled(cron = "0 0 2 * * *", zone = "Asia/Kolkata")           // 02:00 daily, IST

    public void configurablePoll() { }
}

// cron - SIX fields, seconds first
0 0 2 * * *            # 02:00 every day
0 */15 * * * *         # every 15 minutes
0 0 9-17 * * MON-FRI   # hourly, 09:00-17:00, weekdays
0 0 0 1 * *            # midnight on the 1st of each month
AttributeBehaviour
fixedDelayWait N ms after the previous run finishes. Never overlaps. The safe default
fixedRateEvery N ms from the previous start. A slow run means the next queues immediately; on one thread they serialise and drift
cronSix fields: second, minute, hour, day-of-month, month, day-of-week. The leading seconds field is not in Unix cron

The default scheduler pool size is ONE

Every @Scheduled method in the application shares a single thread. One slow job blocks every other job, silently — the symptom is jobs "not running", not an error. Set spring.task.scheduling.pool.size to at least the number of scheduled methods.

12.5 Scheduling across multiple instances

The problem nobody meets in development and everybody meets in production: deploy three replicas and every one runs the job. The customer gets three invoices, or three duplicate rows. @Scheduled is per-JVM.

ApproachAssessment
ShedLockThe usual answer. Takes a lock in a shared store (JDBC, Redis, Mongo) before running. One annotation, no new infrastructure
Quartz with clusteringPersistent jobs, misfire handling, clustering. Right for dynamic schedules or job history; heavy otherwise
An external triggerA Kubernetes CronJob calls one endpoint. Moves scheduling out of the app — often the cleanest
A leader-election profileScheduler on one dedicated replica. Simple, but a single point of failure
DB row locking by handSELECT … FOR UPDATE SKIP LOCKED on a jobs table. Essentially what ShedLock does for you
@Scheduled(cron = "0 0 2 * * *")
@SchedulerLock(name = "nightlyReconcile",
               lockAtLeastFor = "PT5M",        // hold it even if the job is fast (clock skew between pods)
               lockAtMostFor  = "PT30M")       // released if the pod dies mid-run
public void nightlyReconcile() {
    LockAssert.assertLocked();                  // fails fast if misconfigured
}
lockAtMostFor is the important one · make the job idempotent anyway

If a pod is killed mid-job the lock row remains; without a maximum the job never runs again — invisible until someone notices missing data days later. Set it comfortably above the worst realistic runtime. And locks reduce duplicate runs; they do not eliminate them (a lock can expire while a slow job is still working), so the job itself must be idempotent.

12.6 ApplicationEvent and ApplicationEventPublisher

Core concept

Spring's in-process publish/subscribe. One bean announces that something happened without knowing who cares, which decouples a service from the growing list of side effects attached to it. Before: OrderService called mail, audit and search directly and grew a dependency per side effect. After: a new side effect is a new listener class, no change to OrderService.

// the event - a plain record since Spring 4.2, no base class needed
public record OrderPlacedEvent(Long orderId, Long customerId, BigDecimal total) { }

@Service
public class OrderService {
    private final ApplicationEventPublisher events;
    @Transactional
    public Order place(OrderRequest request) {
        Order order = repository.save(toOrder(request));
        events.publishEvent(new OrderPlacedEvent(order.getId(), order.getCustomerId(), order.getTotal()));
        return order;
    }
}
Under the hood: publishing is SYNCHRONOUS by default

ApplicationEventMulticaster invokes every listener on the same thread, in the same transaction, one after another. A slow listener slows the publisher's request. A listener that throws propagates back to the publisher and can roll the whole thing back — sometimes what you want, often a nasty surprise.

Know the limits

In-process and in-memory. If the JVM dies between publish and listener, the event is gone: no persistence, no retry, no delivery guarantee. It decouples classes inside one application; it is not a substitute for Kafka or RabbitMQ across services, and using it as one is a real architectural mistake.

    @EventListener({ OrderPlacedEvent.class, OrderCancelledEvent.class })
    public void onAny(Object event) { }

    @EventListener @Order(1)                                                // listener ordering
    public void first(OrderPlacedEvent event) { }
}

A listener that returns a value publishes that value as a further event — occasionally elegant, more often a surprise. Return void unless you mean it.

The transactional problem

A plain @EventListener runs inside the publisher's transaction. The confirmation email above is sent before the commit — if the commit then fails, the customer has been told about an order that does not exist. In fintech: a "payment received" SMS for a payment that rolled back.

@TransactionalEventListener phases

BEFORE_COMMIT still inside the transaction, can still cause a rollback · AFTER_COMMIT default, the safe place to notify anything outside the database · AFTER_ROLLBACK only on failure · AFTER_COMPLETION either way.

@TransactionalEventListener                                       // phase = AFTER_COMMIT by default
public void onOrderPlaced(OrderPlacedEvent event) { mailService.sendConfirmation(event.orderId()); }  // only if it really committed

@TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
public void onFailure(OrderPlacedEvent event) { metrics.increment("order.rollback"); }

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)             // needed to WRITE - see the trap
public void writeAuditRow(OrderPlacedEvent event) { auditRepository.save(new AuditEntry(event)); }
Two things that catch people out

Writing to the database in AFTER_COMMIT silently does nothing — the transaction has completed, so the write joins no transaction and is never flushed. Add @Transactional(propagation = REQUIRES_NEW). And if there is no transaction at all, a @TransactionalEventListener does not fire — set fallbackExecution = true if you want it to run anyway.

Why ApplicationReadyEvent and not @PostConstruct

Proxies are created after initialisation, so a @Transactional or @Async call from @PostConstruct runs on the raw object and silently does nothing. 13Most-asked questions

The PDF's 25 for a mid-level role plus 7 more. This phase produces a particular kind of question: not "what does this annotation do" but "it isn't working — why?" Nearly every answer comes back to the same fact, which is the point. every round common senior

AOP

What problem does AOP solve, and where are you already using it? every round

Cross-cutting concerns: logging, timing, auditing, security, retries, transactions, caching. They belong to no single class but must happen in many, so without AOP they are copy-pasted into every method — duplicated, easy to forget, and burying the business logic. The point worth making: this is not exotic. @Transactional, @Cacheable, @Async, @Retryable, @PreAuthorize, @Validated are all Spring AOP. If you use Spring, you use AOP; the only question is whether you understand the mechanism when it misbehaves.

Define aspect, join point, pointcut, advice, target and weaving. every round

A join point is where advice could apply — in Spring AOP always a method execution on a bean. A pointcut is an expression selecting which join points. Advice is the code that runs, and when. An aspect combines pointcuts and advice. The target is your real bean; the proxy is the wrapper Spring injects. Weaving links them — Spring does it at runtime by creating proxies during bean post-processing. Add: Spring AOP borrows AspectJ's syntax but uses its own proxy mechanism, which is why it only advises public method calls on beans made from outside the object.

Name the advice types and their order. every round

@Around wraps everything. Inside it: @Before, the target, then @AfterReturning or @AfterThrowing, then @After like a finally, then the rest of @Around after proceed(). Only @Around can change arguments, suppress the call, replace the return value or swallow an exception — it alone receives a ProceedingJoinPoint. Use the weakest advice that does the job.

How would you write a pointcut, and which style do you prefer? common

execution(* com.acme.service..*(..)) is the workhorse: modifier, return type, declaring type, method name, arguments, with * and .. wildcards. But I prefer @annotation(com.acme.Audited): a package pointcut silently stops matching when someone renames a package; an annotation is explicit at the call site, survives refactoring, and is visible to whoever reads the method next. Package pointcuts are fine for blanket concerns like timing every service call.

JDK dynamic proxy vs CGLIB — which does Spring Boot use? every round

A JDK proxy implements the target's interfaces: needs at least one, advises interface methods only. CGLIB generates a subclass: no interface needed, but class and methods must not be final. Boot defaults to CGLIB (proxyTargetClass=true since 2.0), which avoids the classic failure where a bean has an interface, Spring proxies it as the interface, and code injecting the concrete class fails at startup with BeanNotOfRequiredTypeException. Neither can advise private or static methods, and neither intercepts a call the object makes to itself.

Your @Transactional method isn't opening a transaction. Why? every round

Most likely self-invocation: another method in the same class calls it, the call compiles to this.method() and never leaves the object, so the proxy is not in the path. No error, no warning. Other candidates: the method is private, final or static; the class is not a Spring bean; it is called from @PostConstruct, before the proxy exists. Fix: move the method to a separate bean so the call crosses a proxy boundary — usually better design too. Self-injection with @Lazy if they genuinely belong together. Prove it with logging.level.org.springframework.transaction.interceptor=TRACE.

How do you spot a self-invocation bug in code review? common

Any @Transactional, @Async, @Cacheable or @Retryable method whose only call sites are in the same file. If nothing outside the class calls it, the annotation is dead configuration. Worth saying it is one mechanism, not four quirks: all of those are proxies applied in postProcessAfterInitialization, so they all fail the same way.

Several aspects match the same method. What controls the order, and what order do you want? senior

@Order on the aspect class; lower value = outer, first in, last out. Logging outermost (total time, sees every exception); security early (reject before any work or transaction); retry outside the transaction (each attempt needs its own; retrying inside reuses a connection that may be rollback-only); caching outside the transaction (a hit should not open one); transaction innermost. Caveat: @Order orders aspects, not advices within one aspect — two @Befores in one class have undefined order.

What can Spring AOP not do? common

Advise private, static or final methods, final classes, non-bean objects, field access, constructors, or any call an object makes to itself. All follow from one fact: Spring AOP is runtime proxying. Full AspectJ weaves bytecode at compile or load time and has none of those limits, at the cost of an agent or build weaver — almost never worth it; the usual answer is to restructure the code.

How would you implement method-level timing with AOP? common

A custom @Timed annotation, an @Around aspect on @annotation(timed), and Micrometer's Timer.Sample around proceed() in a try/finally, tagging outcome as success or error. Three details that show you have done it: annotation-based pointcut so refactoring cannot silently disable it; stop in a finally so failed calls are measured; and Micrometer already ships @Timed, so check before writing your own.

Would you implement retry with a custom aspect? senior

I can, and it is a good exercise, but I would not ship it. Production retry needs jitter (no synchronised retry storms), a circuit breaker (do not hammer a dead upstream), per-exception classification (never retry a 400), and metrics. Use spring-retry for @Retryable/@Recover, or Resilience4j when you also want circuit breaking, bulkheads and rate limiting. And place retry outside the transaction so each attempt gets its own.

When would you not use AOP? common

For core business logic (invisible at the call site, painful to debug). When correctness depends on five aspects nesting exactly right. On hot paths where the proxy indirection is measurable. When a plain decorator would be clearer, which is often true with two or three classes. AOP earns its keep when the concern is genuinely scattered across many unrelated classes and orthogonal to what they do.

What does @Transactional look like as an aspect, and why does @PostConstruct break it? senior

TransactionInterceptor is an @Around-style MethodInterceptor registered by @EnableTransactionManagement and applied by the same auto-proxy creator; its pointcut is "has @Transactional on the method or class". Proxies are created at postProcessAfterInitialization, which runs after @PostConstruct. So inside @PostConstruct the field this is the raw target and any annotated call is plain Java. The correct home for startup work that needs proxies is ApplicationReadyEvent or a runner.

Async

What does @Async actually do, and what has to be true for it to work? every round

The proxy submits the call to a TaskExecutor and returns immediately, releasing the caller's thread. Requirements: @EnableAsync somewhere; the method public and called from outside the class; return type void, Future or CompletableFuture — anything else is ignored and the caller gets null. It is a proxy, so every AOP limitation applies. "My async method isn't async" is almost always self-invocation.

What happens to an exception thrown inside an @Async void method? common

It is swallowed. No caller waits on a result, so by default nothing logs it and the work silently did not happen. Fix: implement AsyncConfigurer and return an AsyncUncaughtExceptionHandler. If the method returns CompletableFuture, the exception surfaces from join() wrapped in a CompletionException — unwrap with getCause() before catching your own type.

How does a ThreadPoolTaskExecutor decide whether to queue a task or create a thread? every round

Below corePoolSize it creates a new thread even if others are idle. Once core threads exist, tasks go to the queue. Only when the queue is full does it create more, up to maxPoolSize. Beyond that the rejection policy fires. The consequence people get wrong: core=5, max=100, queue=10000 never grows past 5. Keep the queue small for elasticity, and never unbounded — that turns backpressure into an OutOfMemoryError.

Your correlation ID disappears inside an @Async method. Why, and how do you fix it? common

The MDC is a ThreadLocal and the task runs on a different thread, so it starts empty; same for the SecurityContext, request scope and any active transaction. Fix with a TaskDecorator: capture MDC.getCopyOfContextMap() on the submitting thread, restore it inside the Runnable, clear it in a finally so the pooled thread does not leak it into the next task. For security, DelegatingSecurityContextAsyncTaskExecutor.

A colleague says every service method should be @Async so nothing blocks. What do you say? senior

It moves the blocking rather than removing it — the work still occupies a thread, just from a different pool, and if that pool is smaller or its queue unbounded you have made things worse. @Async is right when the caller genuinely does not need the result (emails, audit writes, index updates) and for parallelising independent calls with allOf. As a blanket policy you lose request context, swallow exceptions, break stack traces, and attach a pool-sizing question to every method. If the real problem is thread exhaustion under IO-bound load, the honest answers are virtual threads (spring.threads.virtual.enabled on Java 21) or WebFlux.

Does @Async still matter with virtual threads? senior

Less, for the "free the container thread" motive: with spring.threads.virtual.enabled=true a blocking request thread is cheap, so you no longer offload just to release it. It still matters for fire-and-forget (the caller returns before the work finishes) and for fan-out parallelism. Two cautions: Boot's virtual-thread mode also makes the default @Async executor and scheduler use virtual threads, so bulkheads by pool size stop meaning much; and synchronized blocks pin the carrier before Java 24, so an @Async method holding a lock around IO can still stall.

Scheduling

fixedRate vs fixedDelay vs cron? every round

fixedDelay waits N ms after the previous run finishes: never overlaps, the safe default. fixedRate triggers every N ms from the previous start: if a run takes longer than N the next is already due, and on one thread they serialise and drift. cron is wall-clock with six fields — note the leading seconds field Unix cron lacks — and should always specify a zone.

What is the default scheduler pool size, and why does it matter? common

One. Every @Scheduled method shares a single thread, so one slow job blocks every other job; the symptom is jobs "not running", not an error. Set spring.task.scheduling.pool.size to at least the number of scheduled methods — a one-line change almost every project needs and nobody makes until it bites.

You deploy three replicas and your nightly job runs three times. How do you fix it? every round

@Scheduled is per-JVM. The usual answer is a distributed lock: ShedLock, one annotation backed by a DB or Redis row, only the lock holder runs. The critical setting is lockAtMostFor: if a pod dies mid-job the lock row remains, and without a maximum the job never runs again. Alternatives: Quartz clustering for persistent jobs and misfire handling, or a Kubernetes CronJob calling an endpoint. Either way make the job idempotent — locks reduce duplicate runs, they do not eliminate them.

How would you design an end-of-day settlement job safely? senior fintech

Triggered by cron with an explicit zone (settlement cut-off is a business-time concept). Distributed lock with lockAtMostFor above the worst runtime. The job itself keyed by settlement date and idempotent: re-running for the same date must be a no-op or a safe overwrite, never a double posting. Process in batches with per-batch transactions (TransactionTemplate, Phase 5) so one bad record does not roll back a million. Record progress in a job-run table so a restart resumes rather than restarts. Emit a metric and an alert on "did not run by 02:30", because a silently skipped settlement is worse than a failed one.

Events

What are Spring application events for, and what are their limits? every round

In-process publish/subscribe. A service announces that something happened without knowing who cares, so a side effect becomes a new listener class rather than a new dependency. Since 4.2 the event is a plain record. The limits matter as much: in-memory, in-process, no persistence, no retry, no delivery guarantee. If the JVM dies between publish and listener the event is gone. It is not a substitute for Kafka or RabbitMQ.

Is event publishing synchronous? every round

Yes, by default — same thread, same transaction, listeners one after another. Two consequences: a slow listener slows the publisher's request, and a listener that throws propagates back and can roll the whole transaction back. Adding @Async moves it to the executor and reverses both.

Why would you use @TransactionalEventListener? every round

Because a plain @EventListener runs inside the publisher's transaction, so a confirmation email goes out before the commit — if the commit fails you told a customer about an order that does not exist. @TransactionalEventListener defers to a phase, AFTER_COMMIT by default. Two traps: writing to the database in AFTER_COMMIT silently does nothing (need REQUIRES_NEW), and with no transaction at all the listener does not fire unless fallbackExecution = true.

What changes when you add @Async to an event listener? common

Four things: an executor thread instead of the publisher's; no longer in the publisher's transaction; exceptions swallowed rather than propagating; MDC and SecurityContext empty without a TaskDecorator. The failure mode to design for is the third: the listener throws, nothing rolls back, nothing logs. For anything that must eventually happen, write an outbox row in the same transaction and let a poller publish it.

Where should startup work go: @PostConstruct, a runner, or an event? common

Not @PostConstruct if the work involves @Transactional, @Async or @Cacheable — proxies do not exist yet. ApplicationRunner when the work is part of starting up and should delay readiness; @EventListener(ApplicationReadyEvent.class) when it is a reaction to being ready (cache warming, service registration). Both fire with every proxy in place. @PostConstruct stays right for cheap, self-contained initialisation of the bean's own state.

How do you test that an event was published and a listener ran? senior

@RecordApplicationEvents on a Spring test injects an ApplicationEvents you can query: events.stream(OrderPlacedEvent.class).count(). For the listener side, mock its collaborator and verify. For @TransactionalEventListener the trap is that a @Transactional test rolls back at the end, so AFTER_COMMIT listeners never fire — use TestTransaction.flagForCommit() + end(), or run the test without the test-managed transaction. For @Async listeners, either inject a synchronous executor in the test profile or await with Awaitility.

Events vs direct calls vs a message broker: how do you choose? senior

Direct call when the caller needs the result or must fail if the side effect fails. In-process event when the side effect is optional-ish, inside one deployable, and you want to decouple the growing list of reactions — and you accept it can be lost on a crash. Broker (via an outbox) when the side effect must eventually happen, crosses a service boundary, or needs replay. The tell: if the word "must" appears in the requirement, an in-memory event is the wrong tool.

What is ContextRefreshedEvent firing twice about? senior

Any context refresh publishes it, and a web app can have more than one context (a parent plus a child DispatcherServlet context in classic MVC, or a manual refresh()). Startup work listening to it can therefore run twice. That is why ApplicationReadyEvent is the recommendation: it is a Boot event tied to the SpringApplication run, fired exactly once.

Give the one sentence that covers this phase. every round

A proxy can only intercept calls that pass through it. Self-invocation, private and final methods, @PostConstruct running before the proxy exists, @Async running on the caller's thread, @Cacheable never consulting the cache — one cause, five symptoms.

The aspect that never fires

The advice that returns null
@Around("@annotation(Timed)")
public void time(ProceedingJoinPoint pjp) throws Throwable {
    long t0 = System.nanoTime();
    pjp.proceed();
    log.info("took {}", System.nanoTime() - t0);
}

Every timed method now returns null. An @Around must be declared to return Object and return the result of proceed(); a void around discards it. Also the timing is not in a finally, so failed calls are never measured.

The batch with no transaction
@Service public class ImportService {
    public void importAll(List<Row> rows) { rows.forEach(this::importOne); }
    @Transactional public void importOne(Row row) { repo.save(map(row)); }
}

Runs; no transaction ever opens. Self-invocation: this::importOne never crosses the proxy. Each save runs in Spring Data's own per-call transaction, so a failure halfway leaves half the rows. Fix: move importOne to a RowImporter bean, or self-inject with @Lazy.

Async on the wrong thread
@Service public class SignupService {
    public void signup(User u) { repo.save(u); sendWelcome(u); }
    @Async private void sendWelcome(User u) { mail.send(u); }
}

The email is sent synchronously on the request thread. Two reasons: private cannot be proxied by CGLIB, and it is a self-invocation anyway. Also nothing says @EnableAsync exists. Fix: public method on a separate NotificationService, called from signup.

The pool that never grows
ex.setCorePoolSize(2);
ex.setMaxPoolSize(50);
ex.setQueueCapacity(Integer.MAX_VALUE);

Two threads forever, and an eventual OutOfMemoryError. New threads are only created when the queue is full; an effectively unbounded queue means maxPoolSize is never consulted, and under sustained load the queue grows until the heap is gone. Fix: a small bounded queue (tens to low hundreds), a rejection policy you chose (CallerRunsPolicy for backpressure), a thread-name prefix.

The lost exception
@Async
public void chargeCard(Payment p) {
    gateway.charge(p);            // throws GatewayException on decline
    repo.markCharged(p.id());
}

A declined card vanishes. Exceptions from an @Async void method are swallowed; there is no log line and the caller already returned. Fix: register an AsyncUncaughtExceptionHandler; better, return CompletableFuture and handle it; best, do not make a money-moving call fire-and-forget at all — record intent in an outbox and process it with retries.

The job that runs three times
@Scheduled(cron = "0 0 2 * * *")
public void sendInvoices() { invoiceService.sendAllDue(); }

Fine with one pod; three invoices per customer with three. @Scheduled is per-JVM. Also no zone (02:00 in whatever the container's TZ is) and the method is not idempotent. Fix: ShedLock with lockAtMostFor above the worst runtime, explicit zone, and sendAllDue keyed so a re-run for the same day is a no-op.

The confirmation for an order that does not exist
@Transactional
public Order place(OrderRequest r) {
    Order o = repo.save(toOrder(r));
    events.publishEvent(new OrderPlacedEvent(o.getId()));
    inventory.reserve(o);         // may throw -> rollback

@EventListener public void onPlaced(OrderPlacedEvent e) { sms.send("Order confirmed"); }

The SMS goes out, then the transaction rolls back. A plain listener runs synchronously inside the publisher's transaction, before commit. Fix: @TransactionalEventListener (AFTER_COMMIT). If the listener must also write to the DB, add @Transactional(propagation = REQUIRES_NEW).

The audit row that never appears
@TransactionalEventListener
public void audit(OrderPlacedEvent e) { auditRepo.save(new AuditEntry(e)); }

Runs without error; no row is written. AFTER_COMMIT executes after the transaction completed, so the save joins no transaction and is never flushed. Warm-up that warms nothing

16Cheat sheet

The sentence that carries the phase

A proxy can only intercept calls that pass through it. Self-invocation, private/final/static, @PostConstruct before the proxy exists, @Async on the caller's thread, @Cacheable never consulted — one cause, five symptoms.

Vocabulary

Join point (a method execution on a bean) · pointcut (which ones) · advice (what runs, when) · aspect (the class) · target (your bean) · proxy (what is injected) · weaving (runtime, via BeanPostProcessor at stage 8).

Advice

@Around[ @Before → target → @AfterReturning|@AfterThrowing → @After ]@Around. Only @Around changes args, skips, replaces, swallows. Must return Object; call proceed() exactly once. Prefer the weakest advice.

Pointcuts

execution(mod ret type.method(args)) with * and .. · within · @annotation (preferred: survives refactoring) · @within · bean(*Service) · args · combine with && || ! · name them with @Pointcut.

Proxies

JDK = interfaces, interface methods only, BeanNotOfRequiredTypeException when injecting the class · CGLIB = subclass, Boot default since 2.0, cannot do final/private/static · Objenesis: no constructor needed · Kotlin: all-open.

Self-invocation fixes

Extract to another bean (right) · @Lazy self-injection (ok) · AopContext.currentProxy() (avoid) · AspectJ LTW (rarely). Review rule: annotated method whose only callers are in the same file = dead config. Prove with transaction.interceptor=TRACE.

Ordering

Lower @Order = outer. Logging > security > retry > caching > transaction (innermost, LOWEST_PRECEDENCE by default). Order within one aspect is undefined.

@Async

@EnableAsync · public, called from outside · returns void (exceptions swallowed → AsyncUncaughtExceptionHandler), CompletableFuture (CompletionException, unwrap getCause()), else null · bean named taskExecutor is the default · MDC/SecurityContext/transaction do not follow → TaskDecorator · Boot 3.2+: default pool is real; before: thread per task.

Pool growth

< core → new thread · core reached → queue · queue full → grow to max · max + full → reject. Big queue = max never reached. Never unbounded. CallerRunsPolicy = backpressure. Name your threads. Wait on shutdown. Separate pools = bulkheads.

@Scheduled

fixedDelay end→start (safe) · fixedRate start→start (overlaps/drifts) · cron six fields, seconds first, set zone · default pool size 1 → spring.task.scheduling.pool.size · per-JVM → ShedLock with lockAtMostFor, or CronJob, or Quartz · jobs idempotent.

Events

Plain record, ApplicationEventPublisher · synchronous, same thread, same transaction, exception propagates · @EventListener(condition=...), @Order, return value republishes · @TransactionalEventListener: BEFORE_COMMIT / AFTER_COMMIT / AFTER_ROLLBACK / AFTER_COMPLETION; DB write after commit needs REQUIRES_NEW; no tx → fallbackExecution · @Async listener: new thread, no tx, swallowed, empty MDC · in-memory only → outbox for "must".

Startup work

@PostConstruct for cheap own-state init · runner when it should delay readiness · ApplicationReadyEvent for reactions (fires once; ContextRefreshedEvent can fire twice).

Beyond the PDF

Virtual threads shrink the "free the thread" motive for @Async but not fan-out or fire-and-forget; pool-size bulkheads stop meaning much; pinning on synchronized before Java 24 · @RecordApplicationEvents + TestTransaction.flagForCommit() for testing · Micrometer ships @Timed; spring-retry / Resilience4j ship retry · settlement jobs: zone, lock, idempotent by date, batch transactions, "did not run" alert.

Phase 5 puts this to work immediately: @Transactional is the most important proxy in Spring, and its module is largely a study of what happens when the call does and does not cross the boundary.
