01Servlets → Spring MVC → Spring Boot

You cannot understand Spring Boot by studying Spring Boot. Every convenience it offers is the answer to a specific pain that came before it: what a servlet is, why web.xml became unmanageable, what Spring MVC did about it, and what was still left for Boot to solve.

1.1 Servlet & servlet container

Core concept

A servlet is an ordinary Java class that runs inside a web server and answers an HTTP request. Every Java web framework — Spring MVC, Struts, JSF, Jersey — is built on this one interface. Spring Boot 3.x uses the jakarta.servlet namespace (2.x used javax). Three types: Servlet (the raw interface: init / service / destroy), GenericServlet (protocol-independent, rarely used), HttpServlet (the one you extend — its service() dispatches to doGet / doPost / doPut / doDelete).

// one servlet, one doGet - twelve GET endpoints means a twelve-branch if/else
@WebServlet(urlPatterns = "/demoServlet1/*")
public class DemoServlet1 extends HttpServlet {
    @Override public void init() { /* called ONCE, before the first request */ }

    @Override protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String path = req.getPathInfo();                       // "/firstEndpoint"
        if ("/firstEndpoint".equals(path)) {
            resp.setStatus(200); resp.setContentType("application/json");
            resp.getWriter().write("{\"status\":\"ok\"}");
        } else if ("/secondEndpoint".equals(path)) { /* ... */ }
        else resp.sendError(404);
    }
    @Override public void destroy() { /* called ONCE, on shutdown */ }
}

A servlet is passive — it cannot open a socket, parse HTTP or manage threads. The servlet container (Tomcat, Jetty, Undertow) does that: networking and HTTP parsing, a worker thread pool (Tomcat default 200, server.tomcat.threads.max), the servlet lifecycle (load, instantiate once, init(), route into service(), destroy()), URL routing, sessions (JSESSIONID), filters and listeners.

Thread safety — a classic mid-level question

One instance, many threads. Any instance field on a servlet is shared mutable state; storing per-request data in a field is a race condition, not a style issue. The same reasoning applies to Spring: a singleton controller or service is exactly one object serving every request — keep it stateless, use local variables (they live on each thread's own stack).

public class BadServlet extends HttpServlet {
    private String userId;                            // SHARED across all threads
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) {
        this.userId = req.getParameter("id");          // thread A writes
        process(this.userId);                            // thread B may have overwritten it
    }
}

1.2 web.xml, servlet mapping and the request flow

web.xml (the deployment descriptor, src/main/webapp/WEB-INF/web.xml) tells the container which URL belongs to which servlet, through a deliberate indirection: URL → servlet-name → servlet-class. The name lets one servlet carry several mappings and lets the class be swapped without touching every mapping. Filters, listeners, error pages and session config live in the same file.

Where Spring plugs in

Spring MVC registers its DispatcherServlet against the default pattern /. That is precisely why it sees every request no other servlet claimed — it becomes the single door into your application.

The servlet-era request flow for PUT /demoServlet1/payments/42: (1) client sends the request → (2) Tomcat accepts the connection and assigns a worker thread → (3) Tomcat consults web.xml: /demoServlet1/* → DemoServlet1 → the class → (4) the single servlet instance is located → (5) HttpServlet.service() reads the method and calls doPut() → (6) inside doPut(), req.getPathInfo() returns /payments/42 and your if/else chain parses the 42 by hand. That last line is the whole argument for Spring MVC: you write @PutMapping("/payments/{id}") and receive @PathVariable Long id already parsed and typed.

1.4 The Spring Framework family

"Spring" is used loosely for three different things — being sloppy about this loses marks. Spring Framework is the core library: IoC container, AOP, data access, transactions, the web layer (MVC and WebFlux). Spring MVC is one module inside it: the servlet-based web layer. Spring Boot is a separate project built on top of the framework that configures it for you — not a fork and not a replacement. Underneath everything, the servlet API is still doing the work.

spring-aopProxy-based aspects — quietly powers @Transactional, @Cacheable, @Async, method security

On top sit the projects: Spring Boot, Data, Security, Cloud, Batch, Integration — each versioned independently, each with its own Boot starter. Spring's historical contribution was a consistent programming model with pluggable implementations: keep the same repository code and swap JDBC for JPA, or EhCache for Redis, by changing configuration.

1.5 Spring MVC: DispatcherServlet, Front Controller, HandlerMapping

Core concept

Spring MVC's central decision is the Front Controller pattern: instead of many servlets each registered against its own URL, there is exactly one — the DispatcherServlet, registered against /. It receives every request and decides, in Java, where it goes. Routing moves from XML into the application, and Spring gets one place to hang every cross-cutting concern: exception handling, content negotiation, argument resolution, interceptors, locale resolution.

    private final PaymentService service;
    public PaymentController(PaymentService service) { this.service = service; }   // constructor injection

    @GetMapping("/payment/{id}")
    public PaymentDto get(@PathVariable Long id) { return service.find(id); }   // object -> JSON automatically

// At request time the DispatcherServlet does a lookup, not a scan.
@Controller vs @RestController

@Controller means the return value is a view name and goes to a ViewResolver. @RestController = @Controller + @ResponseBody: the return value is the response body and goes to an HttpMessageConverter. Return a POJO from a plain @Controller and Spring looks for a template named after it and fails with a confusing 404/500.

Registering the DispatcherServlet — the part Boot removes. In plain Spring MVC you extend AbstractAnnotationConfigDispatcherServletInitializer (returning your @Configuration class and the mapping "/") and write an AppConfig with @EnableWebMvc and @ComponentScan. The container discovers the initialiser through the Servlet 3.0 ServletContainerInitializer mechanism. Spring Boot deletes both classes — 1.7 explains what replaces them.

1.6 IoC and Dependency Injection

Core concept

Inversion of Control is the principle: an object should not create or locate its own dependencies — something outside supplies them. Dependency Injection is the specific technique Spring uses to implement it. If pressed: DI is the how, IoC is the what. Normally your code controls object creation; under IoC the framework does — control has been inverted.

// BEFORE - Payment is welded to User
public class Payment {
    private User sender = new User();                 // <-- the problem
    public String getSenderDetails(String id) { return sender.getUserDetail(id); }   // hits the database
}

// AFTER - constructor injection; there is no "new" anywhere in application code
@Component public class User { public String getUserDetail(String id) { /* ... */ } }

@Component
public class Payment {
    private final User sender;
    public Payment(User sender) { this.sender = sender; }        // Spring passes it in
    public String getSenderDetails(String id) { return sender.getUserDetail(id); }
}

// THE PAYOFF - no database, milliseconds to run
@ExtendWith(MockitoExtension.class)
class PaymentTest {
    @Mock User user;                 // a fake, fully under our control
    @InjectMocks Payment payment;    // constructed with the fake
    @Test void returnsSenderName() {
        when(user.getUserDetail("7")).thenReturn("Asha");
        assertEquals("Asha", payment.getSenderDetails("7"));
        verify(user).getUserDetail("7");
    }
}

Why the "before" cannot be unit tested: new User() executes unconditionally, so there is no seam to substitute a mock. Your "unit" test needs a real User → real datasource → real database — slow, flaky, and no longer telling you whether Payment is correct.

FormSyntaxVerdict
Constructorparameters on the constructorPreferred. Fields can be final, the object is never half-built, and the class is testable with plain new. Since Spring 4.3 @Autowired is optional with a single constructor.
Setter@Autowired on a setterAcceptable for genuinely optional dependencies. Field cannot be final.
Field@Autowired on the fieldDiscouraged. Invisible dependencies, no final, class cannot be instantiated outside Spring — exactly what a unit test wants to do.
A frequent follow-up

"If field injection is worse, why does everyone use it?" Because it is three characters shorter and dominated older tutorials. It also hides a design smell: a constructor with eight parameters is obviously doing too much, whereas eight @Autowired fields look tidy. Constructor injection makes bad design visible — which is a feature.

1.7 Spring Boot's three advantages

Spring MVC solved routing, coupling and testability. It left three problems untouched, and those three are what Boot exists to solve.

1 · Dependency management. In Spring MVC you declared every dependency with its own version and owned the compatibility matrix (spring-webmvc 5.3.20 — compatible with jackson-databind 2.13.3? with Hibernate 6?). Boot replaces this with starters and a parent BOM:

<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.5.6</version>                      <!-- the ONLY version you state -->
</parent>
<dependencies>
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-web</artifactId></dependency>   <!-- no version -->
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-test</artifactId><scope>test</scope></dependency>
</dependencies>
Say this precisely

Starters solve transitivity — spring-boot-starter-web is a pom-only artefact with no code that pulls in Spring MVC, Jackson, validation, logging and embedded Tomcat: one line instead of thirty. The parent BOM solves version compatibility — a dependencyManagement block pinning a mutually-tested version for every library Boot knows about. Two different mechanisms; interviewers notice when you conflate them.

2 · Auto-configuration. Boot removes the AppConfig and the initialiser by inferring configuration from the classpath: @EnableAutoConfiguration reads candidate configuration classes from META-INF/spring/…AutoConfiguration.imports in every jar; each is guarded by @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. So DispatcherServletAutoConfiguration applies only because DispatcherServlet is on the classpath and you have not defined one. Full treatment in 07.

The rule that makes it safe

Auto-configuration is backs-off-first. Almost every auto-configured bean is @ConditionalOnMissingBean: define your own and Boot silently steps aside. You are never fighting the framework — you are filling in defaults it offered.

@SpringBootApplication          // = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
public class MyApplication {
    public static void main(String[] args) { SpringApplication.run(MyApplication.class, args); }
}

3 · Embedded server. Under servlets and Spring MVC the server was infrastructure: install Tomcat, version it, build a WAR, copy, restart. Boot inverts this — spring-boot-starter-web brings tomcat-embed-core as an ordinary jar; at startup Boot instantiates Tomcat programmatically and registers the DispatcherServlet with it. java -jar app.jar is the whole deployment procedure, which is what makes Docker images and Kubernetes straightforward.

1.8 Convention over configuration — the opinionated nature

For every decision it can make on your behalf, Boot picks a sensible default rather than asking; you configure only where you disagree. The important half: every default is overridable. An opinion you cannot override is a cage.

A very common bug — the scan convention

Boot scans downward from the main class's package. com.example.app.MyApplication sees controller/, service/, repository/ beneath it; com.example.other.HelperService is a sibling and is never found. Put the main class in com.example.app.config and your service beans stop being found. The main class belongs in the root package.

Three ways to override an opinion, lightest first: a property; define your own bean (@ConditionalOnMissingBean backs Boot off); exclude the auto-configuration (@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)).

The answer that lands

"Spring Framework is the ecosystem — IoC, AOP, data access, web. Spring MVC is the web module inside it, built on the Servlet API, whose front controller is the DispatcherServlet. Spring Boot is not an alternative to either — it is a layer on top that removes configuration through starters, auto-configuration and an embedded server. A Boot web application is a Spring MVC application; the DispatcherServlet is still there, it was just registered for me." If they push — "what does Boot add at runtime?" — very little: Boot is a configuration and packaging concern. At runtime you run Spring Framework beans inside a Spring MVC dispatch cycle.

2.3 pom.xml anatomy

Four things do all the work; everything else is ordinary Maven.

  • The parent — spring-boot-starter-parent inherits from spring-boot-dependencies, a pure BOM with several hundred dependencyManagement entries. It also sets the Java version, UTF-8, resource filtering for application.properties and plugin defaults. Cannot use the parent (corporate parent already)? Import the BOM with <type>pom</type><scope>import</scope> in dependencyManagement — you keep versions, lose only the plugin defaults.
  • The starters — POMs with no classes. -web: MVC, Jackson, Hibernate Validator, Tomcat, json, logging. -data-jpa: Spring Data JPA, Hibernate, HikariCP, tx, jdbc. -test: JUnit 5, Mockito, AssertJ, Hamcrest, JSONassert, MockMvc. -security, -validation, -actuator, -webflux (Netty instead of Tomcat). ./mvnw dependency:tree shows what a starter pulled in.
  • The Spring Boot Maven plugin — without it mvn package produces an ordinary jar with only your classes that will not run. It binds repackage to the package phase and rewrites the jar into an executable fat jar; also gives spring-boot:run and spring-boot:build-image.
  • Exclusions — swap the server by excluding spring-boot-starter-tomcat from -starter-web and adding spring-boot-starter-jetty.

2.6 The application startup lifecycle

From main() to a bound port — eight steps
  1. main() runs, SpringApplication.run() is called with the primary source class.
  2. Application type is deduced from the classpath: SERVLET (spring-webmvc) · REACTIVE (webflux) · NONE.
  3. ApplicationContextInitializers and listeners are loaded from META-INF/spring.factories.
  4. The Environment is prepared — application.yml, env vars, --args merged by precedence.
  5. The ApplicationContext is created and bean definitions registered — component scan finds your classes.
  6. Auto-configuration runs, honouring every @Conditional: beans you defined win, Boot fills the gaps.
  7. Non-lazy singletons are instantiated and injected — constructor injection, then @PostConstruct.
  8. The embedded container starts and binds the port — "Tomcat started on port 8080" → ApplicationRunner / CommandLineRunner.

Auto-configuration deliberately runs after your own definitions are registered — that ordering is what lets @ConditionalOnMissingBean work.

--debug prints the auto-configuration report: every candidate and exactly which condition decided it. spring.main.lazy-initialization=true defers bean creation until first use — a startup win locally, but it turns wiring errors into runtime errors, so keep it out of production.

2.9 JAR vs WAR

app.jar
├── META-INF/MANIFEST.MF        # Main-Class: org.springframework.boot.loader.launch.JarLauncher
│                               # Start-Class: com.example.payment.PaymentServiceApplication
├── org/springframework/boot/loader/...   # the launcher, in plain form
└── BOOT-INF/
    ├── classes/                # YOUR compiled classes and resources
    ├── lib/                    # every dependency, as nested .jar files (~40)
    └── classpath.idx
Why a custom launcher is needed

The standard classloader cannot load classes from a jar nested inside another jar. So the manifest's Main-Class is not your class but Boot's JarLauncher, which installs a classloader that can read BOOT-INF/lib/*.jar, then invokes the Start-Class you wrote. That indirection is the entire trick behind java -jar. A layered jar (default since 2.4) splits BOOT-INF into dependencies / loader / snapshot-dependencies / application so Docker caches the dependency layers and a code change rebuilds a few megabytes.

WAR exists for one situation: an organisation mandating deployment into an existing application server. Three changes: <packaging>war</packaging>; mark spring-boot-starter-tomcat as provided; extend SpringBootServletInitializer and override configure() (keep main so java -jar still works). What you give up: reproducibility — the container version, JVM and shared lib/ live outside your artefact, so the thing you tested is not exactly the thing that runs.

2.10 DevTools, hot reload and the banner

Add spring-boot-devtools with <optional>true</optional> and runtime scope. It gives automatic restart on recompile (~1 s), LiveReload for static resources, development-friendly defaults (template caching off), and disables itself when started from a packaged jar so it cannot reach production.

How the restart is so much faster than a cold start

Two classloaders. Third-party jars never change, so they are loaded once by a base classloader and kept. Your classes go into a throwaway restart classloader. A restart discards and rebuilds only the second one, skipping the load of forty dependency jars. It is a genuine context restart, not HotSwap — which is why it handles new beans and changed signatures reliably.

The banner: replace it with src/main/resources/banner.txt (placeholders ${application.version}, ${spring-boot.version}, ${spring.profiles.active}) or turn it off with spring.main.banner-mode=off. Cosmetic — but printing the version and active profile on every start is genuinely useful when staring at production logs.

Beyond the PDF — Boot 3.x details worth a line each
  • Virtual threads (3.2+): spring.threads.virtual.enabled=true switches Tomcat's request handling and @Async executors to virtual threads on Java 21 — the thread-per-request model stays, the pool-size ceiling goes away. Watch for pinning inside synchronized blocks.
  • Boot 3 → 4: the starters were split — starter-web becomes starter-webmvc, starter-test gains per-technology test starters; Jackson 3; Spring Framework 7. Concepts identical; names differ.
  • Testcontainers (3.1+ @ServiceConnection) is how you replace H2 with a real Postgres in tests — keep H2 out of main scope so it never silently rescues a broken configuration.

03IoC container & beans

Strip away the vocabulary and the container is an ordinary Java object that does three things: holds a map of recipes for creating objects, works out the order to create them, and creates them by reflection and caches them. No bytecode magic in the core — you could write a crude version in an afternoon. Understanding this is the biggest step from "I use Spring" to "I understand Spring".

3.3 What is a bean

Core concept

A bean is simply an object whose creation, wiring and lifecycle are owned by the container. It need not implement an interface, extend a class or follow the get/set convention — the name is historical. What the container stores is a BeanDefinition: beanClassName, scope, lazyInit, dependsOn, primary, constructorArgumentValues, propertyValues, initMethodName/destroyMethodName, factoryBeanName/factoryMethodName (set when the bean comes from a @Bean method).

Bean vs object

Every bean is an object; almost no object is a bean. A DTO you create with new inside a method is not a bean and never will be — Spring does not know it exists, so @Autowired, @Transactional and @Value inside it do nothing. Root cause of a very common beginner bug: annotating a class you then instantiate yourself.

@Service public class ReportService {
    @Autowired private MailSender mailSender;    // works: Spring created this bean
    public void run() {
        Report r = new Report();                 // NOT a bean
        r.send();                                // any @Autowired inside Report is null
    }
}

3.5 @Configuration and @Bean

@Bean declares a bean by writing the code that creates it — for when scanning cannot help, most often because you do not own the class. The method name becomes the bean name (unless name), the return type is the injection type, and method parameters are injected.

@Configuration

    @Bean
    public ObjectMapper objectMapper() {                                   // third-party class
        return JsonMapper.builder().addModule(new JavaTimeModule())
                .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS).build();
    }
    @Bean(name = "primaryDataSource", initMethod = "start", destroyMethod = "close")

Why @Configuration is not just @Component — full mode vs lite mode

A @Configuration class is subclassed at runtime by CGLIB and calls to @Bean methods are intercepted so they return the cached singleton instead of executing the body again (full mode). Cost: the class and its @Bean methods cannot be final. @Bean methods on a plain @Component run in lite mode — no proxy, so an inter-bean call is a plain Java call and creates a new object. @Configuration(proxyBeanMethods = false) opts into lite mode deliberately for startup speed; Boot's own auto-configurations do this.

@Configuration                          // FULL mode
public class GoodConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); }     // intercepted -> the SAME A
    @Bean public C c() { return new C(a()); }     // intercepted -> the SAME A
}
@Component                              // LITE mode
public class BrokenConfig {
    @Bean public A a() { return new A(); }
    @Bean public B b() { return new B(a()); }     // plain Java call -> a NEW A
}

The safe habit: take the dependency as a method parameter rather than calling another @Bean method. Works identically in both modes and is what the framework's own code does.

3.6 @ComponentScan — how scanning actually works

A classpath walk: Spring reads the .class files under the given packages with ASM — without loading them — checks each for a @Component meta-annotation, and registers a BeanDefinition per match.

3.8 Bean naming and @Qualifier

Names: @Component on PaymentService → paymentService (decapitalised); @Component("payments") → payments; @Bean public DataSource mainDs() → mainDs; @Bean(name = {"a","b"}) → a with alias b; URLParser → URLParser (not decapitalised — first two chars uppercase).

Ordering, and an easy mistake

List order comes from @Order, @Priority or Ordered. Without one, the order is effectively arbitrary. And an empty result is a failure by default: if no bean implements the interface, List injection fails unless required = false or ObjectProvider.

4.8 Circular dependencies

Two or more beans that require each other. Since Boot 2.6 they are rejected by default — a deliberate and correct change. With constructor injection neither object can be constructed first, so BeanCurrentlyInCreationException at startup with the cycle printed. Setter injection resolves it because construction and wiring are separate steps — but the cycle is still a design smell.

Option (worst to best)Verdict
spring.main.allow-circular-references=trueDo not. Silences the message without fixing anything and re-enables the fragile early-reference machinery. Temporary unblock during a migration only.
Switch one side to setter or field injectionWorks — the object is constructed empty and wired afterwards. Cycle still there.
Annotate one side @LazyA proxy is injected; the real bean resolves on first use. Tidy, keeps constructor injection. Still a workaround.
Extract the shared behaviour into a third beanThe actual fix. A cycle almost always means two classes share a responsibility that belongs to neither. OrderService → PricingCalculator ← UserService.
Why Spring changed the default in 2.6

The old behaviour exposed a half-constructed singleton to break the cycle. That interacts badly with proxying: the bean handed to the other side could be the raw instance rather than the proxied one, so @Transactional or @Async silently did nothing. Failing at startup is strictly better.

4.10 Optional<T> and ObjectProvider

public MetricsService(Optional<MetricsExporter> exporter) { }       // 1. present or empty, decided once
public MetricsService(@Nullable MetricsExporter exporter) { }       // 2. same idea, plain null

@Service public class ExportService {
    private final ObjectProvider<MetricsExporter> exporters;         // 3. resolves LAZILY, on every call
    public void export() {
        exporters.ifAvailable(e -> e.push());                        // zero or one
        exporters.orderedStream().forEach(e -> e.push());            // all of them, ordered
        MetricsExporter e = exporters.getIfUnique();                 // null if ambiguous
        MetricsExporter f = exporters.getObject();                   // a NEW prototype each call
    }
}
The one to remember

ObjectProvider is the modern, container-friendly answer to "how do I get a new prototype instance from inside a singleton?" It avoids both ApplicationContextAware and method injection, and it is what Spring's own auto-configurations use for optional collaborators.

05Bean scopes & lifecycle

Ten stages, four scopes, and the proxy stage that explains half of Spring's surprises. Being able to name the stages in order — and say which one creates proxies — is the strongest single signal in a Spring Core interview.

5.1 Singleton — the default

One instance per ApplicationContext, created eagerly at startup, cached in the singleton registry, handed to everyone who asks. @Service is implicitly @Scope("singleton").

Spring singleton is NOT the Singleton pattern

The GoF singleton is one instance per classloader, enforced by a private constructor and a static field. A Spring singleton is one instance per container, enforced by nothing — the class has a public constructor and you can new as many as you like. Two contexts in the same JVM (common in tests) give two instances. Asked constantly.

The consequence: singletons must be stateless 
@Service public class BrokenCartService {
    private Cart cart;                                   // SHARED across all requests
    public void addItem(Item item) { cart.add(item); }   // thread A's item lands in thread B's cart
}
@Service public class GoodCartService {
    private final CartRepository repository;             // final, shared, immutable - fine
    public void addItem(String cartId, Item item) {
        Cart cart = repository.find(cartId);             // local variable - per-thread stack
        cart.add(item); repository.save(cart);
    }
}

Injected collaborators are fine (they are stateless singletons); config read once into final fields is fine. Per-request or per-user data is not — method parameters, locals, or a request-scoped bean. In a payment service a shared BigDecimal runningTotal field is a silent money bug.

The container creates a prototype, injects it, runs init callbacks — and then forgets it entirely. @PreDestroy and DisposableBean.destroy() are never called. Web scopes, backed by the current request via a ThreadLocal in RequestContextHolder: request (one per HTTP request), session (per HTTP session), application (per ServletContext), websocket. @RequestScope is shorthand for @Scope(value = "request", proxyMode = TARGET_CLASS) — the proxy is there for a reason: without it, injecting a request-scoped bean into a singleton fails at startup because no request is in progress when singletons are created.

Session-scoped beans and horizontal scaling

A @SessionScope bean lives in one instance's memory. Behind a load balancer the next request may land elsewhere and find an empty cart. Sticky sessions, Spring Session + Redis, or — best — stateless servers with state in a token or database.

The same machinery, everywhere — and why self-invocation fails

Scoped proxies, @Transactional, @Async, @Cacheable and method security are all the same technique: Spring hands you a subclass or interface proxy instead of your object, and the proxy does something before delegating. A proxy can only intercept calls that go through it. When a method calls another method on this, the call never leaves the object — the proxy is bypassed and the annotation appears to do nothing. The single most common Spring bug at mid level.

5.6 The full bean lifecycle — ten stages

Memorise the order, and stage 8
  1. BeanDefinition is read and registered — scanning, @Bean methods, auto-configuration; metadata only
  2. BeanFactoryPostProcessor runs — can EDIT definitions before any object exists; @Value placeholders resolved
  3. Instantiation — the constructor is called; constructor injection happens at this exact moment
  4. Population — @Autowired fields and setters filled in
  5. Aware callbacks — BeanNameAware, BeanFactoryAware, ApplicationContextAware
  6. BeanPostProcessor.postProcessBeforeInitialization() — object exists and is wired, not initialised
  7. Initialisation callbacks — @PostConstruct → InitializingBean.afterPropertiesSet() → initMethod
  8. BeanPostProcessor.postProcessAfterInitialization() — WHERE PROXIES ARE CREATED: @Transactional, @Async, @Cacheable
  9. Bean is ready — singletons cached in the registry; prototypes forgotten immediately
  10. Destruction, on context close — @PreDestroy → DisposableBean.destroy() → destroyMethod; singletons only

Proxies are applied after initialisation. That is why @PostConstruct code runs on the raw object and sees no @Transactional behaviour. Both orderings have the same shape: annotation first, interface second, XML/attribute last.

@Component
public class LifecycleDemo implements BeanNameAware, InitializingBean, DisposableBean {
    public LifecycleDemo(Dependency d)              { out("1 constructor"); }        // stage 3
    @Autowired public void setOptional(Optional<Extra> e) { out("2 setter injection"); }   // stage 4
    @Override public void setBeanName(String n)    { out("3 BeanNameAware"); }      // stage 5
    @PostConstruct public void init()              { out("4 @PostConstruct"); }     // stage 7a
    @Override public void afterPropertiesSet()     { out("5 afterPropertiesSet"); } // stage 7b
    @PreDestroy public void cleanup()              { out("6 @PreDestroy"); }        // stage 10a
    @Override public void destroy()                { out("7 destroy"); }             // stage 10b
}

5.7–5.9 @PostConstruct/@PreDestroy, the interfaces, initMethod/destroyMethod

@PostConstruct/@PreDestroy come from jakarta.annotation — a standard package, so your class stays framework-agnostic. Any visibility (package-private is idiomatic), no arguments. @PostConstruct runs after all injection, so it is the right place for setup that needs dependencies (warming a cache). @PreDestroy runs on graceful shutdown only — not on kill -9, never for prototypes.

The trap: @PostConstruct runs before proxying

Stage 7 comes before stage 8. A @Transactional or @Async method called from inside @PostConstruct runs on the raw, unproxied object — no transaction, no separate thread, silently. For startup work that needs a transaction use an ApplicationRunner or @EventListener(ApplicationReadyEvent.class), both of which fire once the context is fully built and proxies are in place.

    private final ImportService importService;                 // has @Transactional methods

    void onReady() { importService.importAll(); }              // the transaction actually applies

// A BeanPostProcessor that proxies - exactly how @Transactional works
@Component
public class TimingPostProcessor implements BeanPostProcessor {
    @Override public Object postProcessAfterInitialization(Object bean, String name) {
        if (!(bean instanceof PaymentGateway)) return bean;
        return Proxy.newProxyInstance(bean.getClass().getClassLoader(), new Class<?>[]{ PaymentGateway.class },
            (proxy, method, args) -> {
                long t0 = System.nanoTime();
                try { return method.invoke(bean, args); }
                finally { log.info("{}.{} took {} ms", name, method.getName(), (System.nanoTime() - t0) / 1_000_000); }
            });
    }
}
The rule that catches people out

A BeanPostProcessor is instantiated before ordinary beans, so any bean you inject into one is dragged into existence early — before the other post-processors are ready. Environment variables outrank every application.yml, including profile-specific ones. 7.2 @EnableAutoConfiguration — how it works

Seven stages
  1. @EnableAutoConfiguration carries @Import(AutoConfigurationImportSelector.class)
  2. Every jar is scanned for the candidate list: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (spring.factories before 2.7)
  3. Candidates are filtered cheaply on @ConditionalOnClass using pre-computed metadata — classes that cannot match are never loaded
  4. Survivors are ordered: @AutoConfiguration(before/after), @AutoConfigureOrder
  5. They are processed AFTER your own bean definitions — the selector is a DeferredImportSelector; this ordering is what makes @ConditionalOnMissingBean meaningful
  6. Each remaining @Conditional is evaluated — OnBean, OnMissingBean, OnProperty, OnWebApplication, OnResource
  7. Matching configurations register their beans; the whole decision tree is printed by --debug
The sentence that answers the question

"Auto-configuration is a list of candidate @Configuration classes declared in a file inside each jar, imported last, and each guarded by conditions — most importantly @ConditionalOnClass, which keys off what is on the classpath, and @ConditionalOnMissingBean, which makes Boot back off the moment I define my own."

08Most-asked questions

The 60 questions from both phases, merged and deduplicated, pitched at 2–6 years. Nearly every one can be answered badly with a definition and well with a sequence of events — aim for the second. every round common senior

Concepts & the request flow

Difference between Spring, Spring MVC and Spring Boot? every round

Spring Framework is the ecosystem: IoC container, AOP, data access, transactions, web layer. Spring MVC is one module inside it — the servlet-based web stack whose front controller is the DispatcherServlet. Spring Boot is a separate project on top that configures the framework through starters, auto-configuration and an embedded server. The line to land: Boot is not an alternative to MVC — a Boot web app is a Spring MVC app; the DispatcherServlet is still there, registered on my behalf. If pushed on "what does Boot add at runtime?" — very little; it is a configuration and packaging concern.

Walk me through what happens when a request hits a Spring Boot REST endpoint. every round

Eight steps, in order: (1) embedded Tomcat accepts the connection and assigns a worker thread; (2) the filter chain runs — Spring Security lives here; (3) the request reaches the DispatcherServlet, mapped to /; (4) HandlerMapping (RequestMappingHandlerMapping) resolves URL, method, headers, content type to a controller method; (5) HandlerInterceptor.preHandle()s run; (6) the HandlerAdapter resolves arguments — @PathVariable, @RequestParam, @RequestBody via Jackson — validates and invokes; (7) the return value goes through an HttpMessageConverter and is written as JSON; (8) postHandle/afterCompletion, thread back to the pool. Anything thrown is caught by a HandlerExceptionResolver and offered to @ControllerAdvice.

What is the DispatcherServlet and why "front controller"? every round

The single servlet Spring MVC registers, mapped to /, so every request no other servlet claims arrives there. Front Controller is the pattern: one entry point that centralises dispatch. That is what makes exception handling, content negotiation, argument resolution, interceptors and locale resolution possible in one place. In plain MVC you registered it via web.xml or AbstractAnnotationConfigDispatcherServletInitializer; in Boot, DispatcherServletAutoConfiguration does it.

Is a servlet thread-safe? How many instances? common

One instance per servlet declaration, shared across all concurrent requests — so not thread-safe by default; any instance field is shared mutable state. Keep per-request data in local variables on each thread's stack. The identical reasoning applies to Spring singletons — controllers, services, repositories are one object each — and is the real reason a request-scoped bean injected into a singleton needs a scoped proxy.

HandlerMapping vs HandlerAdapter? common

HandlerMapping answers which handler serves this request? — a lookup table built from @RequestMapping metadata at startup, matched on path, method, headers, params, consumes, produces. HandlerAdapter answers how do I invoke it? — normalises the several handler shapes and runs argument resolvers and return-value handlers. Routing and invocation, deliberately separated.

How does a returned Java object become JSON? common

Through an HttpMessageConverter — MappingJackson2HttpMessageConverter, registered because Jackson is on the classpath via starter-web. @RestController's @ResponseBody tells the return-value handler to write the body rather than resolve a view; content negotiation picks the converter from Accept and produces. Customise with a Jackson2ObjectMapperBuilderCustomizer or spring.jackson.*.

Two controller methods map to the same path. What happens? common

Startup fails with IllegalStateException: Ambiguous mapping naming both methods — a startup failure, not runtime, because the mapping table is built during refresh. Mappings are distinguished by more than path: method, params, headers, consumes, produces. Same path is fine if one consumes JSON and the other XML.

Does web.xml still exist in a Boot application? senior

No — an executable jar has no WEB-INF and no external container to read a descriptor. Servlets, filters and listeners are registered as ServletRegistrationBean, FilterRegistrationBean, ServletListenerRegistrationBean beans, or via @ServletComponentScan. web.xml is still valid in a WAR to an external container.

Container, beans, DI

What is the IoC container, in mechanical terms? every round

An ordinary Java object holding a map of BeanDefinitions — recipes for building objects. At startup it resolves the dependency graph, instantiates non-lazy singletons by reflection, injects dependencies, runs lifecycle callbacks and caches them. The distinction worth drawing: definition and instantiation are separate phases; all definitions are registered before any object exists, which is what makes BeanFactoryPostProcessor and @ConditionalOnMissingBean possible.

IoC vs DI? every round

IoC is the principle: an object should not create or look up its own dependencies. DI is the specific technique (constructor, setter, field). DI is one implementation of IoC; Service Locator is another, and a worse one. Normally your code controls creation; under IoC the container does. The payoff is substitutability — and the substitution you care about most is a mock in a unit test.

BeanFactory or ApplicationContext — which, and why? every round

ApplicationContext, always. It extends BeanFactory and adds events, MessageSource, resource loading, the Environment, automatic BeanPostProcessor registration and AOP auto-proxying. The behavioural difference they want: it instantiates non-lazy singletons eagerly at startup, so a missing or ambiguous dependency is a startup failure rather than a production surprise. Fail-fast is the reason for the default.

@Component, @Service, @Repository, @Controller — real differences? every round

All four are detected identically. @Service adds nothing technically — intent only. @Repository enables exception translation into DataAccessException via a post-processor. @Controller is what RequestMappingHandlerMapping looks for when building the routing table. Swap @Service for @Component and nothing breaks; swap @Controller and your endpoints silently disappear.

@Component vs @Bean — when do you need @Bean? every round

Three situations: you do not own the class (ObjectMapper, a vendor client); creation needs logic (builder, conditional, wrapping); you need several beans of the same type — impossible with @Component. Otherwise @Component, because scanning is less to maintain.

Why is @Configuration not simply @Component? common

@Configuration classes are subclassed by CGLIB and calls between @Bean methods are intercepted, so a() called from b() returns the cached singleton — full mode. @Bean methods on a plain @Component run in lite mode: no proxy, an inter-bean call is a plain Java call and creates a second object. proxyBeanMethods = false opts into lite mode for startup speed; Boot's auto-configurations do this. The robust habit: take the dependency as a method parameter.

Why constructor injection over field injection? every round

Four mechanical reasons. Fields can be final, so the object is immutable and safely published. The object is never observable half-built — with field injection the constructor returns before anything is injected, so constructor logic sees null. The class can be constructed in a plain JUnit test with new. A nine-parameter constructor is visibly wrong, whereas nine @Autowired fields look tidy. @Autowired is optional on a single constructor since 4.3; Lombok's @RequiredArgsConstructor removes the boilerplate.

Two beans of the same interface — what happens, how do you fix it? every round

NoUniqueBeanDefinitionException at startup. Resolution order: @Primary on one bean, then @Qualifier at the injection point, then parameter name against bean name. @Qualifier beats @Primary. Use @Primary for an obvious default with a rare exception; @Qualifier when every call site must choose. Prefer a custom qualifier annotation over a string — a typo becomes a compile error.

How would you implement the Strategy pattern with Spring? common

Inject a List of the interface — Spring supplies every implementation, ordered by @Order. Adding a strategy means adding one class; no registry, no switch. Or a Map<String, Strategy> keyed by bean name, ideal when the choice is a runtime value like a payment method. Caveats to volunteer: without @Order the list order is arbitrary, and an empty result fails injection unless ObjectProvider or optional.

Circular dependency — what happens, and the proper fix? every round

Since Boot 2.6, startup fails with BeanCurrentlyInCreationException and a printed cycle; with constructor injection neither can be built first. The workarounds — allow-circular-references=true, setter injection on one side, @Lazy on one parameter — all work and none fix the design. The real fix: extract the shared behaviour into a third bean. Why the default changed: the old mechanism exposed a half-constructed singleton, and the other side could receive the raw instance rather than the proxy, so @Transactional silently did nothing.

What is @Lazy and its two meanings? common

On a bean definition it defers creation until first use. On an injection point it injects a proxy immediately and resolves the real bean on first call — how it breaks a cycle. Use sparingly: it trades startup time for a slower first request and moves wiring errors to runtime.

@Autowired vs @Resource vs @Inject? senior

@Autowired matches by type first; @Resource (Jakarta) by name first, falling back to type; @Inject (JSR-330) like @Autowired without required. Be consistent — @Autowired in a Spring codebase.

Scopes, lifecycle, proxies

Is a Spring singleton the same as the Singleton pattern? every round

No. GoF: one instance per classloader, enforced by a private constructor and static field. Spring: one instance per ApplicationContext, enforced by nothing — public constructor, new as many as you like. Two contexts in one JVM give two instances, which is exactly what happens in a test suite with several context configurations.

Why must singleton beans be stateless? every round

One instance serves every concurrent request on every container thread; a mutable instance field is shared mutable state and will be raced. Fine: final fields holding other stateless singletons, configuration read once. Not fine: anything per-request or per-user — use method parameters, locals, or a request-scoped bean.

How do you get a new prototype instance from inside a singleton? every round

First why it is a problem: the singleton is created once, so its dependencies are resolved once; prototype semantics apply to the act of asking, and a plain @Autowired field asks exactly once. Best fix: ObjectProvider<T> and getObject() per use — type-safe, no framework interface, no proxy. Alternatives: scoped proxy (proxyMode = TARGET_CLASS), @Lookup, or ApplicationContextAware + getBean() — the last is service location; avoid.

Walk me through the bean lifecycle. every round

Definition registered → BeanFactoryPostProcessor may edit it → constructor (constructor injection here) → population (fields, setters) → Aware callbacks → postProcessBeforeInitialization → initialisation (@PostConstruct, afterPropertiesSet(), initMethod) → postProcessAfterInitialization → ready → on shutdown @PreDestroy, destroy(), destroyMethod. The stage that matters: proxies are created in postProcessAfterInitialization — after initialisation. That single fact explains why @Transactional does not work inside @PostConstruct.

@PostConstruct, InitializingBean, initMethod — order, and which to use? common

@PostConstruct → afterPropertiesSet() → @Bean(initMethod). Destruction mirrors it. Annotation, interface, attribute — both times. Use @PostConstruct for your own classes (it is jakarta.annotation, no Spring coupling); initMethod/destroyMethod for third-party classes you cannot annotate; the interfaces are legacy.

Why does @Transactional not work when called from @PostConstruct? every round

@PostConstruct runs at initialisation; proxies are created after initialisation. At that moment your object is the raw instance — no transactional proxy to intercept the call. Move the work later: an ApplicationRunner, or @EventListener(ApplicationReadyEvent.class); both fire once the context is fully built and every proxy is in place.

Are @PreDestroy callbacks guaranteed to run? common

No. They run on a graceful close — SIGTERM via the shutdown hook, or context.close(). Not on kill -9, a JVM crash or power loss, and never for prototypes. Fine for flushing a buffer or closing a pool; never rely on it for correctness — anything that must happen should be idempotent and recoverable on the next start. In a ledger system, that means a journal, not a shutdown hook.

BeanFactoryPostProcessor vs BeanPostProcessor? common

BFPP operates on definitions before any object exists — PropertySourcesPlaceholderConfigurer resolving ${...} is one. BPP operates on instances around initialisation and can return a replacement — how proxying works; AnnotationAwareAspectJAutoProxyCreator creates every @Transactional/@Async/@Cacheable proxy. Gotcha: post-processors are instantiated before ordinary beans, so a bean injected into one is created too early and silently skips its own proxying — inject ObjectProvider.

What is a scoped proxy and when do you need one? common

A stand-in of the same type, injected once into a longer-lived bean, that resolves the correct instance for the current scope on every call. Needed whenever a shorter-lived bean is injected into a longer-lived one — request-scoped into singleton being the standard case; without it injection would happen at startup when no request exists. TARGET_CLASS = CGLIB subclass (no final); INTERFACES = JDK proxy (needs an interface).

Why do @Transactional and friends stop working on internal method calls? every round

The behaviour lives in a proxy, and a proxy can only intercept calls that go through it. A call on this never leaves the object. Applies identically to @Async, @Cacheable, @PreAuthorize, scoped proxies — one mechanism, not four bugs. Fixes: move the annotated method into a separate bean and inject it (cleanest); self-inject with @Lazy; or AspectJ load-time weaving, which does not use proxies.

The single most common Spring bug at this level? common

Self-invocation. Annotate a method @Transactional or @Async, call it from another method in the same class, and it silently does nothing — no error, no log line. Once you know Spring's declarative features are almost all proxies applied in postProcessAfterInitialization, this stops being a surprise — and the same insight explains scoped proxies, method security, and why final classes cannot be CGLIB-proxied.

Configuration & auto-configuration

How does @SpringBootApplication work? every round

A composed annotation: @SpringBootConfiguration (a specialised @Configuration, also the anchor @SpringBootTest looks for), @EnableAutoConfiguration, and @ComponentScan of this package and below. The scan default is why the main class belongs in the root package — move it into a sub-package and its siblings stop being scanned.

Explain auto-configuration end to end. every round

@EnableAutoConfiguration imports AutoConfigurationImportSelector, a DeferredImportSelector — which is what makes it run last, after your configuration and component scan. It reads candidate class names from META-INF/spring/…AutoConfiguration.imports in every jar (spring.factories before 2.7). Candidates are cheaply pre-filtered on @ConditionalOnClass using pre-computed metadata, ordered via @AutoConfiguration(before/after), then processed as normal configuration classes where their conditions decide. Because it runs after your definitions, @ConditionalOnMissingBean reliably sees your beans and backs off. --debug prints the report.

Starter vs auto-configuration? What does starter-parent give you? every round

A starter is a POM with no code — a curated list of transitive dependencies. An auto-configuration is a @Configuration guarded by conditions that actually creates beans. Shipped as two artefacts: x-spring-boot-autoconfigure (code) and x-spring-boot-starter (dependency list); spring-boot-starter-* is reserved, third parties use {name}-spring-boot-starter. starter-parent is separate again: it inherits the spring-boot-dependencies BOM pinning tested versions (why your dependencies carry no <version>) plus Java version, encoding, filtering and plugin defaults. Corporate parent already? Import the BOM with <scope>import</scope>.

How do you override a Boot default? every round

Four levels, always the lowest that works: (1) set a property; (2) define your own bean — @ConditionalOnMissingBean backs Boot off for that one bean; (3) implement a *Customizer — adjusts the object Boot built and inherits future defaults; (4) exclude the auto-configuration — you now own every bean it would have supplied. Level 3 is the underrated one.

Why does @EnableWebMvc break a Boot application? common

It switches off WebMvcAutoConfiguration entirely: you silently lose message converters, static resources, error handling, content negotiation. @EnableWebMvc is for plain Spring MVC. In Boot, implement WebMvcConfigurer — it composes with the auto-configuration.

@Value or @ConfigurationProperties? common

@Value for one or two stray values; @ConfigurationProperties for anything structured — in practice almost everything. It buys validation (@Validated + Jakarta constraints: bad value fails at startup with file and line), relaxed binding, nested/list/map binding, and one type documenting the whole configuration surface. Bind to a record; register with @ConfigurationPropertiesScan or @EnableConfigurationProperties.

Explain property precedence. Why does it matter? every round

Highest first: command-line args, SPRING_APPLICATION_JSON, env vars and system properties, profile files outside the jar, profile files inside, application.yml outside, inside, @PropertySource, defaults on SpringApplication. It is what makes build once, deploy everywhere possible — the byte-identical jar you tested runs everywhere with the platform supplying the differences. Relaxed binding means SERVER_PORT and server.port are the same property.

The config file says one thing but the app behaves differently. How do you debug it? common

Almost always precedence: env vars outrank every application.yml, so a stray SPRING_DATASOURCE_URL in a manifest beats application-prod.yml. Check /actuator/env for which source won. Confirm the active profile — a typo in SPRING_PROFILES_ACTIVE means the overlay never loads, with no warning. Remember lists are replaced, not merged.

How do profiles work, and what should not go in a profile file? common

A named set of beans and properties activated by spring.profiles.active. application-{profile}.yml overlays application.yml; @Profile gates registration and supports !prod, prod & !eu. Profile files decide shape — beans, log levels, pool sizes. Never secrets: they are committed like any other file.

How do you handle secrets? common

Never in a committed file. Baseline: environment variables (visible in /proc, leak into logs). Better: Kubernetes Secrets mounted as files (rotation without redeploy). Best: a secret manager — Vault, AWS/GCP — as a PropertySource so code is unchanged and you gain rotation and an audit trail. Also secure /actuator/env and /actuator/configprops, and rotate any credential that ever touched a commit.

How do you find out why a bean did or did not get auto-configured? common

--debug prints the conditions evaluation report; Negative matches names the exact failed condition — usually a missing class pointing at a forgotten dependency. At runtime /actuator/conditions, /actuator/beans, /actuator/configprops.

A bean you wrote is not being found. Diagnose it. every round

Work down the list: is it in a scanned package (sibling of the main class's package = invisible — the most common cause by far)? Does it have a stereotype, or a @Bean declaration? Is it @Profile-gated or behind a non-matching @Conditional? Are you creating it with new somewhere — an object, not a bean? Then confirm empirically: /actuator/beans or ctx.getBeanDefinitionNames().

Starts locally, fails in production with "Failed to configure a DataSource". Reason about it. common

Locally H2 was on the classpath, so DataSourceAutoConfiguration found an embedded DB and configured it silently. In production there is no embedded DB and no spring.datasource.url, so the same auto-configuration fails fast. Auto-configuration is classpath-driven; an environment difference is a classpath or property-source difference. Fix: supply URL/username/password as env vars; keep H2 in test scope so it never silently rescues a broken configuration.

Walk me through writing your own starter. senior

Five pieces: a @ConfigurationProperties type; the service class; an @AutoConfiguration guarded by @ConditionalOnClass/OnProperty with every @Bean @ConditionalOnMissingBean; registration in META-INF/spring/…AutoConfiguration.imports; a separate starter POM depending on the autoconfigure module plus its libraries. The detail that shows real experience: spring-boot-configuration-processor as an optional dependency for IDE metadata.

How would you speed up a slow-starting Boot application? senior

Measure first — --debug and Actuator's startup endpoint for per-bean timings. Then, in order of payoff: remove unused starters; narrow the scan with basePackageClasses; exclude auto-configurations you do not need; mark expensive rarely-used beans @Lazy individually. Global lazy init is dev-only. For a step change, GraalVM native image resolves conditions at build time. "Boot is slow because of auto-configuration" is only partly fair — the dominant cost is usually scanning and instantiating every non-lazy singleton.

What is inside a fat jar, and why a custom launcher? common

BOOT-INF/classes/ your code, BOOT-INF/lib/ every dependency as a nested jar, org/springframework/boot/loader/ the launcher unpacked. The JDK classloader cannot read a jar nested in a jar, so Main-Class is JarLauncher, which installs a classloader that can and then invokes Start-Class. Layered jars (2.4+) let Docker cache dependency layers.

When would you still build a WAR? senior

Only when an organisation mandates an existing application server. Three changes: war packaging, starter-tomcat as provided, extend SpringBootServletInitializer. Cost: reproducibility — the container, JVM and shared libs sit outside your artefact.

How does DevTools restart faster than a normal restart? senior

Two classloaders: third-party jars loaded once by a base loader and retained; your classes in a disposable restart loader that is the only thing rebuilt. A genuine context restart, not HotSwap, so it handles new beans and changed signatures. Disables itself from a packaged jar.

What happens between main() and "Tomcat started on port 8080"? common

SpringApplication.run() deduces the application type from the classpath, loads initialisers and listeners, prepares the Environment by precedence, creates the ApplicationContext, registers definitions via scanning, applies auto-configuration honouring every condition, refreshes — instantiating singletons, injecting, running @PostConstruct — starts the embedded server, then invokes ApplicationRunner/CommandLineRunners. Volunteer the ordering: auto-configuration runs after your definitions, which is what makes @ConditionalOnMissingBean meaningful.

09What's wrong with this code?

Twelve snippets that look fine and are not. Say what breaks, when (startup or runtime), and the fix — then open the answer.

The shared cart
@Service public class CartService {
    private Cart cart = new Cart();
    public void add(Item i) { cart.add(i); }
}

Runtime, under load. A singleton with a mutable field: every request shares one Cart. Thread A's item lands in thread B's cart. Fix: per-request data in parameters/locals or a repository lookup by id; or a @RequestScope/@SessionScope bean with its scoped proxy.

The annotated object that is not a bean
@Component public class Report { @Autowired MailSender mail; void send() { mail.send(); } }
@Service public class ReportService { public void run() { new Report().send(); } }

Runtime NPE. new Report() is an object, not a bean; Spring never sees it, so mail is null. Inject Report (or an ObjectProvider<Report> if you need fresh instances) instead of constructing it.

Transactional warm-up
@Service public class Loader {
    @PostConstruct void init() { importAll(); }
    @Transactional public void importAll() { /* many writes */ }
}

Runs, silently without a transaction. Two problems: @PostConstruct runs before the proxy exists (stage 7 vs 8), and it is a self-invocation anyway. Move the work to @EventListener(ApplicationReadyEvent.class) and call the transactional method on an injected bean.

Lite mode
@Component public class ClientConfig {
    @Bean public HttpClient client() { return HttpClient.newHttpClient(); }
    @Bean public PaymentClient payments() { return new PaymentClient(client()); }
    @Bean public RefundClient  refunds()  { return new RefundClient(client()); }
}

Runtime: three HttpClients. @Component means lite mode — client() is a plain Java call each time. Use @Configuration, or better, take HttpClient as a method parameter so it works in both modes.

The tidy package
com.example.app.config.PaymentApplication      // @SpringBootApplication
com.example.app.service.PaymentService         // @Service

Startup: NoSuchBeanDefinitionException for anything that needs PaymentService. The scan starts at com.example.app.config; service is a sibling. Move the main class to com.example.app.

Two constructors
@Service public class SearchService {
    public SearchService(IndexClient index) { this(index, Cache.noop()); }
    public SearchService(IndexClient index, Cache cache) { }
}

Startup failure — with more than one constructor Spring cannot choose (it falls back to a no-arg one, which does not exist). Annotate the one Spring should use with @Autowired.

The prototype that isn't
@Component @Scope("prototype") public class ReportBuilder { private final List<Row> rows = new ArrayList<>(); }
@Service public class ReportService {
    private final ReportBuilder builder;
    public ReportService(ReportBuilder builder) { this.builder = builder; }
    public Report build(...) { builder.add(...); return builder.done(); }
}

Runtime: rows accumulate across calls. Injected once into a singleton, the prototype is effectively a singleton. Inject ObjectProvider<ReportBuilder> and call getObject() per build.

The default that hides an outage
@Value("${payment.gateway.url:http://localhost:8081}") String gatewayUrl;

Runtime, in production, quietly. A missing property no longer fails startup; production silently calls localhost. A gateway URL has no safe default — drop the default, or use @ConfigurationProperties with @NotBlank.

The vanishing servers
# application.yml          app.servers: [ a, b, c ]
# application-prod.yml     app.servers: [ d ]

Production sees only d. Lists are replaced, not merged. Model additive config as a map, or list everything in the profile file.

The endpoint that disappeared
@Component @RequestMapping("/api/payments")
public class PaymentController { @GetMapping public List<PaymentDto> all() { } }

Trick — this one works, because a type-level @RequestMapping is also detected by RequestMappingHandlerMapping. Remove the class-level @RequestMapping and keep @Component, and the endpoints silently vanish. Also: without @ResponseBody/@RestController the list is treated as a view name. Use @RestController.

The eager post-processor
@Component public class AuditingPostProcessor implements BeanPostProcessor {
    private final AuditService audit;              // @Transactional inside
    public AuditingPostProcessor(AuditService audit) { this.audit = audit; }
}

Runtime: AuditService's @Transactional does nothing (and Spring logs "is not eligible for getting processed by all BeanPostProcessors"). Post-processors are created before ordinary beans, so AuditService was built too early and skipped proxying. Inject ObjectProvider<AuditService> and resolve lazily.

Turning MVC off by accident
@Configuration @EnableWebMvc
public class WebConfig implements WebMvcConfigurer { @Override public void addCorsMappings(CorsRegistry r) { } }

Runtime: JSON dates, static files, error pages behave differently. @EnableWebMvc disables WebMvcAutoConfiguration. Delete the annotation; implementing WebMvcConfigurer alone composes with Boot.

11Cheat sheet

Two sentences carry both phases

The container registers every definition before it creates any object — explains auto-configuration, @ConditionalOnMissingBean, BeanFactoryPostProcessor. It may hand you a proxy instead of the object you wrote — explains @Transactional, @Async, @Cacheable, scoped proxies, method security, self-invocation, and why a final class cannot be CGLIB-proxied.

Request flow (8)

Tomcat thread → filter chain (Security) → DispatcherServlet on / → HandlerMapping → interceptors preHandle → HandlerAdapter (argument resolvers, validation, invoke) → HttpMessageConverter → postHandle/afterCompletion. Exceptions → HandlerExceptionResolver → @ControllerAdvice.

Startup (8)

main() → deduce type → initialisers/listeners → Environment → context + definitions (scan) → auto-configuration (after yours) → singletons instantiated + injected + @PostConstruct → server bound → runners.

Bean lifecycle (10)

definition → BFPP → constructor → population → Aware → BPP.before → @PostConstruct / afterPropertiesSet / initMethod → BPP.after = proxies → ready → @PreDestroy / destroy / destroyMethod.

Injection resolution

by type → one: inject · none: fail (unless optional) · many: @Primary → @Qualifier (wins) → parameter name → NoUniqueBeanDefinitionException.

Precedence (high → low)

CLI args → SPRING_APPLICATION_JSON → env vars → -D → profile yml outside jar → profile yml inside → yml outside → yml inside → @PropertySource → defaults. Lists replace, maps merge.

Override levels

1 property → 2 your own bean (OnMissingBean) → 3 *Customizer → 4 exclude.

Traps in one line each

  • Main class in a sub-package → siblings not scanned.
  • new on an annotated class → object, not bean; annotations dead.
  • @Bean calling @Bean in a @Component → lite mode, new instances.
  • Prototype @Autowired into a singleton → injected once; use ObjectProvider.
  • @Transactional in @PostConstruct or via this → no proxy, no transaction.
  • Bean injected into a BeanPostProcessor → created early, skips proxying.
  • Web scope without proxy into a singleton → startup failure.
  • @EnableWebMvc in Boot → MVC auto-configuration off.
  • Env var beats application-prod.yml → check /actuator/env.
  • Secrets in a profile file → in git forever; rotate.

Startup failures

NoSuchBeanDefinitionException scan/stereotype · UnsatisfiedDependencyException no/many candidates · BeanCurrentlyInCreationException cycle · Failed to configure a DataSource JPA without URL · Port already in use.

Final word

If you can draw the DispatcherServlet flow from memory, name the ten lifecycle stages and say which one creates proxies, and explain why @ConditionalOnMissingBean has to run after your own definitions — you have Phases 1 and 2. Phase 3 builds the web layer on top; Phase 4 takes the proxy idea apart properly in AOP and transactions.
