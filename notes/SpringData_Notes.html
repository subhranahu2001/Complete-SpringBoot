13JDBC & Spring Data JPA

The largest module in the curriculum. Mapping, relationships, fetching, the persistence context, and the performance decisions that determine whether the application survives real data. Almost everything here works on a hundred rows and fails on a million.

13.1 JDBC and its pain points

Everything sits on JDBC. The failure modes you meet later — connection leaks, exhausted pools, vendor-specific errors — are all JDBC failures wearing a costume.

// twenty-five lines to read one row
public Order findById(Long id) {
    Connection con = null; PreparedStatement ps = null; ResultSet rs = null;
    try {
        con = dataSource.getConnection();
        ps  = con.prepareStatement("SELECT id, status, total FROM orders WHERE id = ?");
        ps.setLong(1, id);
        rs  = ps.executeQuery();
        if (rs.next()) { Order o = new Order(); o.setId(rs.getLong("id")); /* ... */ return o; }
        return null;
    } catch (SQLException e) { throw new RuntimeException(e); }        // checked, nowhere to go
    finally {
        try { if (rs  != null) rs.close();  } catch (SQLException ignored) { }
        try { if (ps  != null) ps.close();  } catch (SQLException ignored) { }
        try { if (con != null) con.close(); } catch (SQLException ignored) { }
    }
}
  • Resource management is manual. One missed close() in one branch leaks a connection; the pool is exhausted hours later, long after the deploy that caused it.
  • SQLException is checked and vendor-specific. Error code 23505 is a unique-key violation on PostgreSQL and something else on Oracle.
  • Row-to-object mapping is boilerplate that grows with every column. No transaction abstraction beyond setAutoCommit(false) and manual commit/rollback.
Four levels of abstraction over the same JDBC calls

Plain JDBC (Connection, PreparedStatement, try/finally) → JdbcTemplate (you write SQL; Spring handles resources and exception translation) → JPA / Hibernate (entities, persistence context, dirty checking, lazy loading) → Spring Data JPA (repository interfaces, derived queries, no implementation to write). Higher is not automatically better; each layer trades control for brevity. Hibernate still issues JDBC; Spring Data still uses an EntityManager.

When to prefer JdbcTemplate over JPA

Reporting and analytics, bulk operations, hand-tuned SQL, and read paths where you want no persistence context at all. Mixing is normal and healthy: JPA for the transactional domain model, JdbcTemplate (or jOOQ) for queries JPA expresses badly. Choosing one for the whole application on principle is the mistake.

Exception translation is the quiet win

Because the class is @Repository, a PersistenceExceptionTranslationPostProcessor proxies it and converts vendor SQLExceptions into DuplicateKeyException, DataIntegrityViolationException, CannotAcquireLockException and so on. Your service catches something meaningful without knowing which database is underneath — the real reason @Repository is not just documentation.

13.3 ORM and Hibernate fundamentals

Core concept

An ORM maps rows to objects and, crucially, tracks them. That tracking is where all the power and all the surprises come from. JPA is the specification; Hibernate is the implementation Boot ships. The chain: @Service @Transactional method → Spring Data repository proxy → EntityManager, one per transaction (persistence context = 1st-level cache, dirty checking at flush, write-behind queue) → JDBC connection borrowed from HikariCP, released at commit.

ConceptWhat it is
EntityA class mapped to a table, with an identity
EntityManagerThe JPA API for persisting, finding, querying. Hibernate's Session implements it
Persistence contextThe set of entities the EntityManager is tracking. The first-level cache. One per transaction
Dirty checkingAt flush, Hibernate compares each managed entity against the snapshot taken at load and issues UPDATEs for what changed. You never call save() for an update
FlushWriting pending SQL. At commit, before a query that might conflict, or on explicit flush()
Write-behindSQL is queued, not immediate, so Hibernate can batch and reorder
The mental model that prevents most JPA bugs

JPA is not a SQL generator you call. It is a unit of work: load objects, modify them, and at commit Hibernate works out the minimum SQL. Almost every "why did it run that query?" or "why did my change not persist?" comes from thinking method-by-method instead of transaction-by-transaction.

IDENTITYDB auto-incrementSimple, but disables JDBC batch inserts — Hibernate must execute each INSERT immediately to learn the id
SEQUENCEDB sequencePreferred where supported. Allows batching; allocationSize fetches ids in blocks
TABLEA table as a sequencePortable and slow. Avoid

ORDINAL is the default and stores the enum's position. Insert a constant in the middle and every existing row silently changes meaning. Always @Enumerated(EnumType.STRING). It costs a few bytes and makes the column readable.

equals and hashCode on entities

Do not generate from all fields, and do not use a DB-generated id naively — it is null before persist, so an entity added to a HashSet before saving becomes unfindable afterwards. Safe options: a business key, or a natural id assigned in the constructor. If in doubt, leave the defaults alone.

13.5 Relationships

@Entity public class Order {
    @ManyToOne(fetch = FetchType.LAZY)                  // ALWAYS make these lazy
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)   // inverse side
    private List<OrderItem> items = new ArrayList<>();

    @OneToOne(fetch = FetchType.LAZY, cascade = CascadeType.ALL)
    @JoinColumn(name = "invoice_id")
    private Invoice invoice;

    @ManyToMany
    @JoinTable(name = "order_tag", joinColumns = @JoinColumn(name = "order_id"),
               inverseJoinColumns = @JoinColumn(name = "tag_id"))
    private Set<Tag> tags = new HashSet<>();

    // keep both sides consistent - this is not optional
    public void addItem(OrderItem item)    { items.add(item);    item.setOrder(this); }
    public void removeItem(OrderItem item) { items.remove(item); item.setOrder(null); }
}
Owning side vs inverse side

The owning side has the foreign key (OrderItem.order with @JoinColumn); the inverse side declares mappedBy. Only the owning side is written.

The most common relationship bug

order.getItems().add(item) updates an in-memory list; the order_id column lives on OrderItem, so unless you also set item.setOrder(order) nothing is written — or the column is null and the insert fails. Always provide an addX helper on the parent that maintains both sides.

@ManyToMany, and why to avoid it · use Set not List

A @ManyToMany hides a join table you almost always end up needing to describe: when was the tag added, by whom. Model the join table as its own entity with two @ManyToOnes from the start. And with a List, Hibernate deletes every join row and reinserts the remainder on any change; with a Set it issues one DELETE.

13.6 Fetch types: EAGER vs LAZY

AssociationJPA defaultWhat you should use
@ManyToOneEAGERLAZY, always

@OneToManyLAZYLeave it lazy
@ManyToManyLAZYLeave it lazy
EAGER by default on the to-one side is a design mistake in the specification

Every findById silently joins or issues extra selects for associations you may not want, and there is no way to opt out per query — EAGER is a mapping-level decision that overrides your intent. LAZY is the reverse: the default you can opt out of, per query, with a fetch join. Set every association lazy and fetch what you need explicitly.

13.7 Cascade types and orphanRemoval

Cascading propagates an EntityManager operation from parent to children. It is convenience, not a database constraint — it does nothing about foreign-key ON DELETE. PERSIST, MERGE, REMOVE, REFRESH, DETACH, ALL.

CascadeType.REMOVEorphanRemoval = true
Deletes children when…the parent is deletedthe parent is deleted or a child is removed from the collection
order.getItems().remove(item)row orphaned with a null FK, or the flush failsthe row is deleted
Use forLoosely owned childrenTrue composition — an OrderItem has no meaning without its Order
Do not cascade to shared entities · bulk deletes bypass all of this

CascadeType.ALL on a @ManyToOne Customer means deleting one order deletes the customer — and every other order. Cascade flows parent to child in a composition; if the other side can exist independently, it is not a child. And @Query("DELETE FROM Order o WHERE o.status = 'DRAFT'") issues one SQL statement: no entities loaded, so no cascade, no orphanRemoval, no lifecycle callbacks, and a stale persistence context. Often what you want — just know you opted out of the object model; consider clearAutomatically = true.

13.8 The repository hierarchy

Extend the level you actually need

Repository (marker) → CrudRepository (save, findById, findAll, delete, count) → PagingAndSortingRepository (findAll(Pageable), findAll(Sort)) → JpaRepository (flush, saveAndFlush, deleteInBatch, getReferenceById, List return types). Spring Data generates the implementation at runtime. Since Spring Data 3.0, PagingAndSortingRepository no longer extends CrudRepository — extend both if you need both.

public interface OrderRepository extends JpaRepository<Order, Long> { }

@Transactional
public void markPaid(Long id) {
    Order order = repository.findById(id).orElseThrow();
    order.setStatus(PAID);
    // no save() needed - dirty checking issues the UPDATE at commit
}

OrderItem item = new OrderItem();
item.setOrder(orderRepository.getReferenceById(orderId));   // lazy proxy, no SELECT issued
itemRepository.save(item);
save() does not always issue an INSERT

save() checks whether the entity is new — by default, id is null (or Persistable.isNew()). If not new it calls merge(), which may issue a SELECT before the UPDATE. For an already-managed entity, save() is entirely redundant: dirty checking writes the change at commit. Calling it inside a transaction on a loaded entity is harmless but reveals a misunderstanding. And getReferenceById with a missing id gives EntityNotFoundException later, when the proxy is first touched — possibly outside the transaction.

Bulk @Modifying queries and the stale persistence context

A bulk UPDATE or DELETE runs directly in the database. Hibernate does not know which entities it affected, so anything already loaded is stale — a subsequent read may return the old value from the first-level cache. Use @Modifying(clearAutomatically = true, flushAutomatically = true).

Pagination with JOIN FETCH on a collection

Combining JOIN FETCH on a @OneToMany with Pageable makes Hibernate log HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory. It fetches every matching row and paginates in Java — fine for a hundred rows, fatal for a million. 13.12 The N+1 problem

The single most common performance defect in JPA applications

One query for the parents, then one per parent for the children. 100 orders = 101 round trips. It never shows up in a unit test and rarely in a small dataset.

@Transactional(readOnly = true)
public List<OrderSummary> listAll() {
    List<Order> orders = repository.findAll();                                    // 1 query
    return orders.stream().map(o -> new OrderSummary(o.getId(), o.getItems().size())).toList();   // N queries
}
// 1. JOIN FETCH - explicit, one query
@Query("SELECT DISTINCT o FROM Order o LEFT JOIN FETCH o.items")
List<Order> findAllWithItems();

// 2. @EntityGraph - declarative and reusable
@EntityGraph(attributePaths = { "items", "customer" })
List<Order> findByStatus(OrderStatus status);

// 3. @BatchSize on the association - N+1 becomes 1 + N/50
@OneToMany(mappedBy = "order") @BatchSize(size = 50)
private List<OrderItem> items;

// 4. a projection - never load the entities at all
@Query("SELECT new com.acme.dto.OrderSummary(o.id, COUNT(i)) FROM Order o LEFT JOIN o.items i GROUP BY o.id")
List<OrderSummary> summaries();
FixTrade-off
JOIN FETCHOne query, but rows multiply by collection size and it cannot combine with pagination on a collection
@EntityGraphSame effect, declarative, reusable. The usual first choice
@BatchSizeBatches the extra queries rather than eliminating them. Works with pagination. A very good default on collections (or hibernate.default_batch_fetch_size globally)
ProjectionUsually best for read paths. Narrow SELECT, nothing loaded, nothing tracked, no lazy loading possible
logging.level.org.hibernate.SQL=DEBUG                 # see every statement
logging.level.org.hibernate.orm.jdbc.bind=TRACE       # and the bound parameters
spring.jpa.properties.hibernate.generate_statistics=true   # query counts per session
Make it fail the build

Log inspection finds N+1 only when someone looks. Add datasource-proxy or QuickPerf to integration tests and assert a maximum query count per endpoint. A regression then breaks CI on the pull request that introduced it, not production three months later. A very strong thing to say in an interview.

13.13 Entity lifecycle and the persistence context

Four states — only MANAGED entities are dirty-checked

Transient (new Order(), no id, unknown) →persist()→ Managed (tracked, dirty-checked, returned from the 1st-level cache) →close→ Detached (has an id, not tracked; a setter changes nothing in the DB). merge() returns a new managed copy — it does not make the original managed. remove() → Removed, deleted at flush.

Under the hood: why you do not call save() to update

(1) Transaction begins, an empty persistence context is created. (2) findById() loads the row and takes a snapshot of the original field values. (3) You call a setter — no SQL yet. (4) Flush is triggered: at commit, before a conflicting query, or explicitly. (5) Hibernate compares entity against snapshot; only changed columns become an UPDATE. (6) SQL sent, commit, context cleared, connection returned to the pool.

The first-level cache surprises people twice

First: findById(1L) twice in one transaction issues one query and returns the same instance. Second: a bulk @Modifying update bypasses it, so a subsequent read can return the pre-update value. The second-level cache is different: shared across transactions, off by default, per entity with @Cache; useful for small reference data and a good way to introduce staleness bugs on anything else. Module 15's application cache is usually the better tool.

13.14 Projections

Four ways to get data out

Entity (every column, tracked, dirty-checked; heaviest, use when you intend to modify) · Interface projection (Spring builds a proxy; closed or open) · DTO/record projection (constructor expression; narrow SELECT, nothing tracked) · Native + interface (column names map to getters).

// 1. interface projection - Spring generates the implementation
public interface OrderSummary { Long getId(); String getReference(); BigDecimal getTotal(); String getCustomerName(); }   // traverses order.customer.name
List<OrderSummary> findByStatus(OrderStatus status);

// 2. open projection with SpEL - loads the WHOLE entity, computes afterwards
public interface OrderView { @Value("#{target.reference + ' (' + target.status + ')'}") String getLabel(); }

// 3. record projection via constructor expression
public record OrderSummaryDto(Long id, String reference, BigDecimal total) { }
@Query("SELECT new com.acme.dto.OrderSummaryDto(o.id, o.reference, o.total) FROM Order o")
List<OrderSummaryDto> summaries();

// 4. dynamic projection - caller picks the shape
<T> List<T> findByStatus(OrderStatus status, Class<T> type);
Projections are the real fix for a lot of JPA pain

No lazy loading, so no LazyInitializationException and no accidental N+1. Nothing tracked, so no dirty-checking overhead and no unintended UPDATE. And the API shape stops being coupled to the entity — the DTO argument from Phase 3 arriving from the other direction. Keep interface projections closed (plain getters) if the reason is performance; an open one with @Value cannot narrow the SELECT.

@Configuration @EnableJpaAuditing(auditorAwareRef = "auditorAware")

public abstract class Auditable {

Auditing fields are not an audit trail · bulk updates skip auditing too

They tell you who last touched a row, not what changed or what it was before. And AuditingEntityListener is a JPA lifecycle callback, so a @Modifying bulk UPDATE leaves updatedAt untouched — set it explicitly in the query.

13.16 Connection pooling with HikariCP

spring:
  datasource:
    url: jdbc:postgresql://db:5432/payments
    hikari:
      maximum-pool-size: 10            # see the sizing note
      minimum-idle: 10                 # = maximum for a steady-state service
      connection-timeout: 30000        # how long a thread waits for a connection
      idle-timeout: 600000
      max-lifetime: 1800000            # keep BELOW any database or proxy idle timeout
      leak-detection-threshold: 60000
      pool-name: payments-pool
Bigger pools are usually slower

The pool is a ceiling on database concurrency, not a performance dial. Past the DB's cores and disks, more connections mean more context switching and lock contention. HikariCP's guidance starts from roughly connections = (cores × 2) + effective_spindles, often about 10. Multiply by replica count and check against max_connections, leaving headroom for migrations and admin sessions — 10 replicas × 50 connections exhausts a 100-connection server instantly.

SettingGuidance
maximum-pool-sizeStart small (10), raise only with evidence. Total across replicas well under the server limit
minimum-idleEqual to maximum for steady load — a fixed-size pool has more predictable latency
connection-timeoutHow long a thread blocks. Exceeding it throws rather than hanging forever
max-lifetimeShorter than any idle timeout on the DB, load balancer or proxy, or you hand out connections the other end already closed
leak-detection-thresholdLogs a stack trace when a connection is held too long. Invaluable and cheap
The classic pool-exhaustion cause

A @Transactional method that makes a slow HTTP call. The connection is held for the whole call, so ten concurrent requests exhaust a pool of ten and everything else queues on connection-timeout. Never do IO inside a transaction. Load your data, commit, then call out. (Fintech: the payment-gateway call belongs outside the transaction that records the attempt.)

Write migrations that survive a rolling deploy

During a rolling deploy, old and new versions run simultaneously against one schema, so a migration must be backward compatible: add a nullable column, deploy code that writes both, backfill, then drop the old column in a later release (expand/contract). Renaming a column in a single migration takes the old pods down instantly.

13.18 Optimistic and pessimistic locking

Two users load the same order and both save. Without a strategy the second write silently overwrites the first — the lost update problem.

// optimistic - the default choice
@Entity public class Order { @Version private long version; }     // Hibernate manages it - never set it yourself
// every UPDATE becomes:  UPDATE orders SET status = ?, version = 4 WHERE id = ? AND version = 3
// 0 rows affected -> OptimisticLockingFailureException

// conflicts are expected - retry the WHOLE transaction
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3, backoff = @Backoff(delay = 50))
@Transactional
public void applyDiscount(Long id, BigDecimal pct) {
    Order order = repository.findById(id).orElseThrow();
    order.setTotal(order.getTotal().multiply(ONE.subtract(pct)));
}

// pessimistic - when contention is high
@Lock(LockModeType.PESSIMISTIC_WRITE)                                          // SELECT ... FOR UPDATE

14Transaction management

@Transactional is a proxy — Phase 4 applied to the most important annotation in Spring. Propagation, isolation, rollback rules, and why it sometimes does nothing. In a payments system this module is where money goes missing.

14.1 ACID, briefly

PropertyGuaranteeWhat breaks without it
AtomicityAll statements succeed, or none doA transfer debits one account and fails before crediting the other
ConsistencyOne valid state to another, honouring constraintsAn order referencing a customer that does not exist
IsolationConcurrent transactions do not see each other's partial workA report totals half-applied changes
DurabilityOnce committed, survives a crashA confirmed payment disappears after a restart

Spring implements none of this — the database does. Spring provides demarcation: where a transaction begins and ends, expressed declaratively. Atomicity and durability are effectively absolutes; isolation is a dial, and every position trades correctness against concurrency (14.4).

14.2 How @Transactional actually works

@Service

    public Order place(OrderRequest request) {

Under the hood: what the proxy does around that call

(1) Asks the PlatformTransactionManager for a transaction, honouring propagation. (2) Binds the Connection/EntityManager to the current thread in a ThreadLocal held by TransactionSynchronizationManager. (3) Invokes your method. (4) Normal return: flush the persistence context and commit. (5) Unchecked exception: roll back. (6) Either way, unbind and release the connection.

The ThreadLocal binding is why everything else works

Your repository does not receive the connection as a parameter — it looks it up from the thread. That is how several repositories in one method share a transaction automatically. It is also why the transaction does not follow an @Async call or a new thread: different thread, different ThreadLocal, no transaction.

REQUIRES_NEW costs a second connection

The outer transaction is suspended, not closed, so both are held at once. A pool of ten now supports five concurrent requests through this path. Combine with a slow inner operation and you have a pool-exhaustion incident. Use it deliberately, and never inside a loop.

The unexpected rollback 
@Transactional public void outer() {
    try { inner(); }                                // REQUIRED - same transaction
    catch (Exception e) { log.warn("ignoring", e); } // you swallowed it...
    repository.save(somethingElse);
}
@Transactional public void inner() { throw new IllegalStateException(); }

Fails at commit with UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only. When inner() threw, the shared transaction was marked rollback-only — catching does not unmark it. Ways out: prevent the marking (noRollbackFor), or give inner() its own transaction with REQUIRES_NEW.

readOnly does two things: sets the JDBC connection read-only, which lets some drivers and proxies route to a read replica; and tells Hibernate to skip dirty checking and use FlushMode.MANUAL — no snapshots, no flush at commit. Put readOnly on every query method

Free, documents intent, removes a real cost.         this.txTemplate.setTimeout(30);

14.9 Distributed transactions and Saga

Once one operation spans two databases, or a database and a message broker, ACID stops being available. This is where most microservice data problems begin.

Two-phase commit, and why it is out of fashion

XA/2PC: a coordinator asks every participant to prepare, then tells them all to commit. Real atomicity across resources, at a price: locks held through prepare, throughput collapses, the coordinator is a single point of failure, and if it dies between phases participants are left in doubt and blocked. Kafka and most cloud databases do not support it well.

Saga — a sequence of local transactions

Each service commits locally and publishes an event. If a later step fails, earlier steps are undone by compensating actions rather than rollback — you cannot un-commit, so you issue a refund rather than reversing a debit.

ChoreographyOrchestration
HowEach service listens for events and reactsA central orchestrator tells each service what to do next
CouplingLow — no service knows the whole flowThe orchestrator knows everything
VisibilityPoor. The process exists only as an emergent property of the listenersGood. One readable state machine
Best forTwo or three stepsFour or more, or anything with real money
The transactional outbox — the answer to a common design question

"How do you make sure the database write and the Kafka publish both happen?" You cannot make them atomic — separate resources. Publishing before commit risks announcing something that rolls back; after, the process may die in between. Write the event to a table in the same local transaction, then publish it separately.

@Transactional
public Order place(OrderRequest request) {
    Order order = repository.save(toOrder(request));
    outboxRepository.save(new OutboxEvent("OrderPlaced", order.getId(), toJson(order)));   // SAME transaction, same database
    return order;                                                                          // both rows commit or neither does
}

// a separate poller publishes and marks rows as sent - at-least-once delivery
@Scheduled(fixedDelay = 1000) @SchedulerLock(name = "outboxPublisher")
public void publishPending() {
    outboxRepository.findUnpublished(100).forEach(e -> { broker.publish(e); e.markPublished(); });
}

Delivery becomes at-least-once, which is why every consumer must be idempotent. That trade — give up exactly-once, make consumers idempotent — is the core of distributed data handling. (Debezium/CDC can replace the poller by tailing the outbox table from the DB log.)

15Caching

Cheap wins and expensive mistakes. The abstraction, the providers, and the invalidation problem nobody solves cleanly. Caching trades freshness for latency and load — that is the whole deal, and every cache bug is someone forgetting they made that trade.

15.1 Why cache, and where it belongs

Good candidates: expensive to compute, read far more often than written, tolerant of being slightly stale — reference data, configuration, permission lookups, aggregations, third-party API responses (FX rates with a 30 s TTL). Measure before you cache

A cache adds a serialisation format, an eviction policy, an invalidation strategy, an extra failure mode and a class of bug that only appears under concurrency. If a query is slow because it is missing an index, caching it hides the problem and doubles the complexity. Fix the query first; cache what is still slow.

15.3 @Cacheable, @CachePut, @CacheEvict, @Caching

Under the hood

Caller → @Cacheable proxy computes key = #id and looks it up. HIT: return the cached value; the method body never runs, no database round trip. MISS: run the method, store the result under the key, return it. That is the point, and also the source of every surprise.

@Service
public class ProductService {
    @Cacheable(cacheNames = "products", key = "#id")
    public Product findById(Long id) { return repository.findById(id).orElseThrow(); }   // only runs on a miss

    @Cacheable(cacheNames = "products", key = "#id", unless = "#result == null")
    public Product findOrNull(Long id) { }

    @Cacheable(cacheNames = "search", key = "#criteria.hashCode()", condition = "#criteria.cacheable")   // evaluated BEFORE the call
    public List<Product> search(SearchCriteria criteria) { }

    @CachePut(cacheNames = "products", key = "#product.id")
    public Product update(Product product) { return repository.save(product); }     // ALWAYS runs, then refreshes the entry

    @CacheEvict(cacheNames = "products", key = "#id")
    public void delete(Long id) { repository.deleteById(id); }

    @CacheEvict(cacheNames = "products", allEntries = true)
    public void reloadCatalogue() { }

    @Caching(evict = { @CacheEvict(cacheNames = "products", key = "#product.id"),
                       @CacheEvict(cacheNames = "search", allEntries = true) })          // any search may be stale
    public void deactivate(Product product) { }
}
AnnotationRuns the method?Effect
@CacheableOnly on a missPopulates the entry
@CachePutAlwaysOverwrites the entry with the new result
@CacheEvictAlwaysRemoves one entry, or all
@Caching—Groups several of the above on one method
condition vs unless · beforeInvocation on evict

condition is evaluated before the call, can reference arguments only, and decides whether to consult the cache at all. unless is evaluated after, can reference #result, and decides whether to store what came back; unless = "#result == null" is the common one, since caching "not found" is usually wrong. And @CacheEvict runs after the method by default — if the method throws, the entry is not evicted. beforeInvocation = true when a stale entry is worse than an unnecessary eviction.

@Cacheable("orders") on findMyOrders(OrderStatus status) keys on the status alone. 15.9 Caching pitfalls

1 · Self-invocation, again — same mechanism, third appearance 
public List<Product> findAll(List<Long> ids) { return ids.stream().map(this::findById).toList(); }   // NEVER hits the cache
@Cacheable("products") public Product findById(Long id) { }

this::findById does not pass through the proxy. Identical to @Transactional and @Async, fixed the same way: another bean, or @Lazy self-injection.

2 · Caching mutable objects · 3 · Caching entities

An in-process cache stores a reference. Mutate the returned object and you have corrupted the entry for every later caller. Cache immutable types — records — or return a defensive copy; Redis avoids this by serialising. And do not cache JPA entities: a cached entity is detached, touching a lazy association throws, passing it to a repository triggers a merge you did not intend, and a stale @Version causes spurious optimistic-lock failures. Cache DTOs.

4 · Caching failures and nulls

Caching null means a product created a second later stays invisible for the whole TTL. Caching nothing on a miss leaves you open to a lookup storm on non-existent keys. Middle ground: a short negative TTL — cache the absence for thirty seconds, not ten minutes. unless = "#result == null" is the default posture.

5 · No observability — an unmeasured cache is a guess

Enable recordStats() and export cache.gets, cache.puts, cache.evictions and the hit ratio. A cache with a 5% hit rate is pure overhead plus a staleness risk, and you never know unless you look. A very good closing answer to "how do you know your cache is working?"

JPA

What is the persistence context, and why does it matter? every round

The set of entities the EntityManager is tracking — the first-level cache, one per transaction. Two behaviours follow. Dirty checking: Hibernate snapshots each entity at load and compares at flush, issuing UPDATEs for what changed, which is why you never call save() to update a loaded entity. Identity: findById(1L) twice in one transaction issues one query and returns the same instance. Thinking transaction-by-transaction rather than method-by-method is what stops JPA feeling unpredictable.

Explain the entity lifecycle states. every round

Transient: new Order(), no identity, unknown. Managed: in the persistence context, tracked and dirty-checked. Detached: was managed but the context closed; has an id, changes not written. Removed: scheduled for deletion at flush. Practical consequence: a setter on a detached entity does nothing; merge() returns a new managed instance and does not make the original managed.

You call setStatus() on a loaded entity and don't call save(). Does the change persist? every round

Yes, if you are inside a transaction and the entity is managed — dirty checking issues the UPDATE at flush. Calling save() is harmless but redundant, and signals a mental model of JPA as a SQL generator. Conversely, with no transaction the entity is detached and the change is silently lost — that is the version of this question to be ready for.

What is the N+1 problem and how do you fix it? every round

One query fetches N parents; touching a lazy association on each issues N more. Four fixes: JOIN FETCH in a @Query (one query, cannot combine with pagination on a collection); @EntityGraph (same effect, declarative, usually my first choice); @BatchSize (batches the extra queries and, unlike a fetch join, works with pagination); or a projection, often best on a read path because no entities load at all. Detection: org.hibernate.SQL logging, and better, assert a maximum query count per endpoint with datasource-proxy so a regression fails CI.

EAGER or LAZY: the defaults and what should you use? every round

To-one defaults to EAGER, to-many to LAZY. The to-one default is a specification mistake: every findById silently joins associations you may not want and you cannot opt out per query. Make everything LAZY and fetch explicitly with a fetch join or entity graph. LAZY is the default you can opt out of; EAGER is not.

What is LazyInitializationException and how do you fix it properly? every round

Touching a lazy association after the persistence context has closed. Correct fixes: fetch what you need inside the transaction (JOIN FETCH, @EntityGraph) or map to a DTO before it ends. EAGER fixes one call site and pessimises every other. The fix I argue against is open-in-view, on by default in Boot: it holds a DB connection through view rendering and hides N+1 in the serialisation layer. Turn it off on day one.

Explain the owning side of a relationship. common

The side with the foreign-key column; the inverse side declares mappedBy. Only the owning side is written. So order.getItems().add(item) alone changes nothing — you must also call item.setOrder(order). A helper on the parent that maintains both sides is standard practice.

CascadeType.REMOVE vs orphanRemoval? common

REMOVE deletes children when the parent is deleted. orphanRemoval also deletes a child removed from the collection. Use it for true composition. The trap: CascadeType.ALL on a @ManyToOne Customer means deleting one order deletes the customer and all their orders. Cascade flows parent to child; if the other side can exist independently, it is not a child.

Does save() always issue an INSERT? common

No. It checks whether the entity is new — by default id is null. If not, it calls merge(), which may SELECT before the UPDATE. For an already-managed entity inside a transaction it is redundant: dirty checking writes at commit.

When would you use JdbcTemplate instead of JPA? common

Reporting and analytics, bulk operations, hand-tuned SQL, read paths with no persistence context. Mixing is normal: JPA for the transactional domain model, JdbcTemplate or jOOQ for queries JPA expresses badly. Choosing one for everything on principle is the mistake. @Repository gives exception translation to DataAccessException either way.

What's wrong with @Enumerated default behaviour? common

The default is ORDINAL, storing the position. Insert a constant in the middle and every existing row silently changes meaning — data corruption with no error. Always @Enumerated(EnumType.STRING).

How would you map money in JPA? senior fintech

BigDecimal with explicit @Column(precision = 19, scale = 4) (or the currency's minor units), never double. Currency as a separate @Enumerated(STRING) or 3-char column. Better: an @Embeddable Money(amount, currency) value object so arithmetic and rounding live in one place. Store in the DB as NUMERIC, not FLOAT. Balances are updated with an atomic conditional UPDATE, not read-modify-write. And an @Version on anything two users can touch.

Interface projection vs DTO projection: when each? senior

Closed interface projection (plain getters) is the least code and Spring narrows the SELECT; it returns a proxy, which is fine for reads but awkward to build in tests. A record via constructor expression is explicit, immutable, cacheable, and works with @Query and native. Open projections with @Value load the whole entity, so they lose the performance benefit. Dynamic projections (Class<T> parameter) let one method serve several shapes.

Data access

How do you size a connection pool? every round

Smaller than people expect. Past the DB's cores and disks, more connections mean context switching and lock contention, not throughput; HikariCP's guidance starts around (cores × 2) + spindles, often about 10. Multiply by replica count, check against max_connections, leave headroom. Keep max-lifetime below any idle timeout in between. The classic exhaustion cause: a @Transactional method making a slow HTTP call. Never do IO inside a transaction.

How should schema changes be managed? every round

Flyway or Liquibase, with ddl-auto: validate in production so a missed migration fails at startup. update is not an option: never drops or renames, cannot be reviewed, environments diverge. The operational detail: during a rolling deploy old and new run simultaneously, so migrations must be backward compatible — add nullable column, write both, backfill, drop later. Renaming in one migration takes the old pods down.

Optimistic vs pessimistic locking? every round

Optimistic: a @Version column in the WHERE clause; zero rows affected means someone else got there first, exception at write time, no DB lock. Pessimistic: a real row lock with SELECT … FOR UPDATE; others block until commit. Optimistic when conflicts are rare (usual); pessimistic when likely or retry is unacceptable: seat booking, stock decrement, account balances. Always set a lock timeout.

Two requests decrement the same account balance concurrently. Walk me through what can go wrong and your fix. senior fintech

Read-modify-write under READ_COMMITTED: both read 100, both subtract 30, both write 70 — a lost update, 30 gone. Fixes in order of preference: an atomic conditional UPDATE (SET balance = balance - 30 WHERE id = ? AND balance >= 30, check rows affected); @Version with a retry loop; PESSIMISTIC_WRITE with a timeout when contention is high. Plus an append-only ledger so the balance is derivable, and an idempotency key on the request so a client retry does not decrement twice.

What does @Repository actually do beyond stereotype scanning? common

It enables exception translation: PersistenceExceptionTranslationPostProcessor proxies the bean and converts vendor SQLExceptions and JPA exceptions into Spring's DataAccessException hierarchy (DuplicateKeyException, DataIntegrityViolationException, CannotAcquireLockException). Spring Data repositories get it automatically. Your service can catch something meaningful without knowing the database.

Transactions

How does @Transactional actually work? every round

A proxy asks the PlatformTransactionManager for a transaction, binds the connection/EntityManager to the thread in a ThreadLocal, invokes the method, commits on return or rolls back on an unchecked exception, then unbinds. The ThreadLocal is why several repositories share a transaction without passing anything — and why it does not follow an @Async call or new thread.

Where should @Transactional go? every round

The service layer, where one business operation begins and ends. Not the controller (stretches across serialisation, holds a connection too long, encourages lazy loading in the view). Not the repository (Spring Data already makes each method transactional; adding your own means two writes in a service are no longer atomic).

Your @Transactional method isn't rolling back on an exception. Why? every round

Most likely a checked exception: Spring rolls back on RuntimeException and Error only; checked commits. Fix: rollbackFor = Exception.class, or better, unchecked domain exceptions. If it is already unchecked, the transaction probably does not exist at all: self-invocation, private/final, a different thread. Prove with transaction.interceptor=TRACE.

Explain REQUIRED vs REQUIRES_NEW. every round

REQUIRED (default) joins or starts: one transaction, one commit, everything rolls back together. REQUIRES_NEW always starts a new one and suspends the outer, so inner work commits independently — audit rows that must survive the caller's rollback. Cost: two connections held at once; a pool of ten supports five concurrent requests through that path. Never in a loop.

What is UnexpectedRollbackException? common

An inner REQUIRED method threw, marking the shared transaction rollback-only. The outer caught and swallowed it and carried on, but catching does not unmark, so the commit fails. Ways out: noRollbackFor to stop the marking, or REQUIRES_NEW to isolate the inner. Lesson: you cannot swallow an exception from a method sharing your transaction and expect to continue.

What does readOnly = true actually do? common

Sets the JDBC connection read-only (some drivers/proxies route to a read replica), and tells Hibernate to skip dirty checking and use manual flush mode — no snapshots, no flush at commit, a measurable saving on large result sets. A hint, not a guarantee. On every query method, usually as a class-level default overridden on writes.

Explain isolation levels and which anomaly each prevents. common

READ_UNCOMMITTED nothing; READ_COMMITTED dirty reads; REPEATABLE_READ also non-repeatable reads; SERIALIZABLE also phantoms. Isolation.DEFAULT means the database's default: PostgreSQL and Oracle READ_COMMITTED, MySQL/InnoDB REPEATABLE_READ — identical code behaves differently. Raising isolation is rarely the fix: READ_COMMITTED plus @Version solves the lost-update problem far more cheaply than SERIALIZABLE.

When would you use TransactionTemplate over @Transactional? common

When the transaction should cover part of a method (keep a slow HTTP call outside it), when the boundary is dynamic, when you want per-iteration transactions so each batch commits or fails independently, or when you are not in a bean. It also gives status.setRollbackOnly(). Otherwise @Transactional stays the default.

How do you make a database write and a Kafka publish atomic? every round

You cannot — separate resources, and 2PC is impractical with Kafka. The transactional outbox: write the row and an outbox row in the same local transaction; a poller (or Debezium CDC) publishes unpublished rows and marks them sent. Delivery becomes at-least-once, so consumers must be idempotent. That trade is the core of distributed data handling.

What is a Saga? common

A sequence of local transactions across services, each committing and publishing an event; a failure at step four is undone by compensating actions (a refund, not a reversed debit). Choreography: services react to events, low coupling, poor visibility. Orchestration: a coordinator drives an explicit state machine, more coupling, far better visibility. Choreography for two or three steps; orchestration for longer flows or anything involving money.

Design the transaction boundary for "charge card, then record the payment". senior fintech

Never call the gateway inside a DB transaction (pool exhaustion, and you cannot roll back a charge). Sequence: transaction 1 inserts a payment row in state PENDING with the idempotency key (commit); call the gateway outside any transaction with a timeout; transaction 2 updates the row to CHARGED or FAILED with the gateway reference. If the process dies between 1 and 3, a reconciliation job queries the gateway by our idempotency key and repairs the state. The PENDING row is what makes the crash recoverable; the gateway-side idempotency key is what makes the retry safe.

Your service is fine for months, then every request starts timing out on getConnection(). What happened? senior

Pool exhaustion. Candidates in order: a new @Transactional method that makes an external call, holding the connection for the call's duration; a REQUIRES_NEW path that doubled connection use; a pessimistic lock without a timeout stalling a queue of threads; a leak from a hand-written JDBC path missing a close(); or traffic simply exceeding pool × (1 / avg tx time). Diagnose with Hikari's leak-detection-threshold, hikaricp.connections.active/pending metrics, and a thread dump showing what the holders are waiting on.

Caching

How does @Cacheable work, and what has to be true for it to fire? every round

A proxy checks the cache for a key derived from the arguments; on a hit it returns the value and the method body never runs; on a miss it calls the method and stores the result. Requirements: @EnableCaching, a public method, and a call from outside the class — this::method bypasses the proxy, the same self-invocation problem as @Transactional and @Async.

@Cacheable vs @CachePut vs @CacheEvict? every round

@Cacheable runs the method only on a miss; @CachePut always runs it and overwrites the entry; @CacheEvict removes one or all. Detail: @CacheEvict runs after the method by default, so if the method throws the entry stays; beforeInvocation = true flips that.

condition vs unless? common

condition is evaluated before the call and references arguments only: whether to consult the cache at all. unless is evaluated after and can reference #result: whether to store. unless = "#result == null" is the common one, because caching "not found" means an entity created a second later stays invisible for the whole TTL.

What's the most dangerous caching bug you can think of? every round

A key that omits the current user. @Cacheable("orders") on findMyOrders(status) keys on status alone, so every user shares one entry and the first caller's orders are served to everyone. A data-leak incident that passes every single-user test. Any cached method whose result depends on the caller must put the caller in the key explicitly.

Should you cache JPA entities? common

No. A cached entity is detached: lazy associations throw, passing it to a repository triggers an unintended merge, a stale @Version causes spurious lock failures. Cache DTOs, ideally immutable records — which also avoids the in-process trap that the cache stores a reference and mutating it corrupts the entry.

What is a cache stampede and how do you prevent it? common

A popular key expires and every concurrent request misses at once, spiking the database precisely when the item is most popular. Jitter the TTL; lock on refresh so one caller reloads (Caffeine's LoadingCache per key); or refresh ahead with refreshAfterWrite, where the first request after the interval gets the stale value and triggers an async reload so nobody blocks.

TTL or explicit eviction: how do you decide? common

Explicit eviction is correct until someone adds a write path that skips it: a bulk @Modifying, a migration, an admin tool, another service. If more than one thing can write the data, TTL is the safer design — it bounds staleness without depending on memory. Versioned keys are a good middle ground for bulk-reloaded reference data.

How do you know your cache is actually helping? common

Measure. recordStats() and export gets, puts, evictions and hit ratio through Micrometer. A 5% hit rate is pure overhead plus staleness risk. Also make the cache optional: a short client timeout and a CacheErrorHandler that logs and falls through, so a Redis outage slows the service rather than taking it down.

Caffeine or Redis for a service with five replicas? senior

Depends on whether replicas must agree. Reference data that can differ by a few seconds harmlessly: Caffeine, short TTL, no network hop. Anything where a user could see an update on one pod and not another (permissions, feature flags, prices): Redis, or Caffeine as a near-cache in front of Redis with pub/sub invalidation. Large caches that would bloat the heap: Redis. And for a rate limiter or idempotency store, it is not a cache at all — it must be shared and consistent, so Redis with atomic operations.

What can you cache in a payments service, and what must you never cache? senior fintech

Cache: FX rates (30 s TTL, refresh-ahead), merchant configuration, fee schedules, BIN lookups, permission checks with the user in the key. Never cache: account balances, transaction status, anything read to make an authorisation decision on money, and anything with PAN or secrets in it (a cache is another place data leaks from). For "must be exact" reads, hit the database with readOnly transactions and a read replica instead.

The update that reads stale data

The debit without a credit

}

The audit that dies with the order

    @Transactional public void place(OrderRequest r) {
        Order o = repo.save(toOrder(r));
        recordAudit("ORDER_PLACED", o.getId());

The lock that hangs the service

Everyone's orders

The cache that never shrinks

19Cheat sheet

The sentence that carries the phase

Everything here behaves perfectly on a hundred rows; the discipline is imagining a million. N+1 is invisible in a unit test. A pool of ten is generous until a transaction makes an HTTP call. open-in-view works until it issues four hundred queries per request. A cache is fast until two users share a key.

Two defaults that are wrong for production and on by default

spring.jpa.open-in-view=false · @Enumerated(EnumType.STRING). Add: every to-one association LAZY; ddl-auto=validate; a real cache provider with a size limit.

Persistence context

One per transaction · transient → managed (persist) → detached (close) / removed · merge() returns a new instance · only managed entities are dirty-checked · snapshot at load, compare at flush, UPDATE only changed columns · never save() to update · same id twice = one query · bulk @Modifying bypasses it → clearAutomatically.

Mapping

SEQUENCE + allocationSize for batching; IDENTITY disables it · UUIDv7 over random · owning side = FK; only it is written; addX() helpers · @ManyToMany → a join entity; Set not List · cascade parent→child only; orphanRemoval for composition · equals/hashCode: business key or leave alone.

N+1

JOIN FETCH (one query, no pagination on collections) · @EntityGraph (first choice) · @BatchSize (works with pagination) · projection (best for reads) · detect with org.hibernate.SQL, enforce with datasource-proxy in tests.

Queries

Derived up to ~3 criteria; then @Query or Specification · JPQL validated at startup, native not · constructor expressions for DTOs · Page = +COUNT, Slice = size+1 · fetch join + Pageable = in-memory → two-query pattern · closed interface projections narrow the SELECT, open ones do not.

Pool & schema

Size ≈ cores×2 + spindles (~10), × replicas < max_connections · max-lifetime < any proxy idle timeout · leak-detection-threshold · never IO inside a transaction · Flyway/Liquibase + validate · expand/contract for rolling deploys.

Locking

@Version default; retry the whole transaction · PESSIMISTIC_WRITE for balances/stock, always with lock.timeout · best for money: atomic conditional UPDATE, check the row count.

@Transactional

Proxy: get tx → bind to ThreadLocal → invoke → commit / rollback on unchecked → release · service layer · REQUIRED default; REQUIRES_NEW = second connection, never in a loop; NESTED not in JPA · swallowed inner exception → UnexpectedRollbackException · checked exceptions COMMIT → unchecked hierarchy or rollbackFor · readOnly on every query, timeout on big tables · does nothing on: self-invocation, private/final/static, new, @PostConstruct, another thread · prove with transaction.interceptor=TRACE · TransactionTemplate for partial/dynamic/per-batch boundaries.

Isolation

RU < RC (no dirty) < RR (no non-repeatable) < SER (no phantom) · DEFAULT = the engine's: PG/Oracle RC, MySQL RR · RC + @Version beats SERIALIZABLE.

Distributed

2PC: locks, SPOF, in-doubt — avoid · saga: local txs + compensations; orchestration for money · outbox: event row in the same transaction, poller/CDC publishes, at-least-once, idempotent consumers.

Caching

@EnableCaching; public, called from outside · @Cacheable miss-only / @CachePut always / @CacheEvict after (beforeInvocation) · condition before (args), unless after (#result) · user in the key · stable, short, immutable keys · Caffeine single-instance, Redis shared; default map never evicts · JSON serialiser, not JDK · CacheErrorHandler + short timeout · stampede: jitter, lock-on-refresh, refreshAfterWrite · TTL beats explicit eviction when >1 writer; versioned keys for bulk reloads · cache DTOs not entities; records not mutables; short negative TTL · recordStats() and look at the hit ratio.

Beyond the PDF

Money: BigDecimal/NUMERIC, embeddable value object, ledger + derived balance · charge-then-record: PENDING row, gateway outside the tx, outcome in tx 2, reconcile on restart · pool-exhaustion triage order · Debezium as the outbox poller · payments cache list: rates/config/fees yes, balances/status/PAN never.
