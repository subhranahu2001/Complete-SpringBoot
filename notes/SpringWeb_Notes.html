08REST APIs with Spring MVC

Phase 2 established that the container creates your objects and may hand you a proxy. This module puts the web layer on top — and most of it is less about annotations than about decisions that are cheap now and expensive to reverse later: DTOs versus entities, pagination, status codes, and one consistent error shape.

8.1 @Controller vs @RestController

Core concept

@RestController is @Controller + @ResponseBody applied to every method. The difference is what Spring does with your return value, and it is a fork in the road, not a preference. @Controller: a returned String is a view name handed to a ViewResolver → templates/orders.html. @RestController: the returned object is the response body, written by an HttpMessageConverter → {"id":7,"total":19.99}.

@Controller                                    // server-rendered HTML
@RequestMapping("/orders")
public class OrderPageController {
    @GetMapping("/{id}")
    public String view(@PathVariable Long id, Model model) {
        model.addAttribute("order", service.find(id));
        return "orders/detail";                   // -> templates/orders/detail.html
    }
}

@RestController                                // JSON API
@RequestMapping("/api/orders")
public class OrderApiController {
    @GetMapping("/{id}")
    public OrderResponse get(@PathVariable Long id) {
        return service.find(id);                 // -> serialised straight to the body
    }
}
The bug this causes

Return a DTO from a plain @Controller and Spring treats toString() as a view name, then fails to find a template with that name. The error mentions circular view path or a missing view and says nothing about serialisation, so it reads as unrelated. If a JSON endpoint suddenly returns HTML or a 500 about views, check the class annotation first.

You can mix them: @Controller on the class with @ResponseBody on individual methods is exactly what @RestController does in bulk. Only worth it when one class genuinely serves both pages and JSON — rare, and usually worth splitting.

8.4 ResponseEntity and status codes

Returning a plain object gives you 200 OK and nothing else. ResponseEntity gives full control of status, headers and body; @ResponseStatus on the method is lighter for the "always this status" case.

@PostMapping
public ResponseEntity<OrderResponse> create(@RequestBody @Valid CreateOrderRequest r) {
    OrderResponse created = service.create(r);
    URI location = ServletUriComponentsBuilder.fromCurrentRequest()
            .path("/{id}").buildAndExpand(created.id()).toUri();
    return ResponseEntity.created(location)            // 201 + Location header
            .eTag("\"" + created.version() + "\"")
            .body(created);
}

@GetMapping("/{id}")
public ResponseEntity<OrderResponse> get(@PathVariable Long id) {
    return service.findOptional(id)
            .map(ResponseEntity::ok)
            .orElseGet(() -> ResponseEntity.notFound().build());
}

@DeleteMapping("/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)                  // 204, no ResponseEntity needed
public void delete(@PathVariable Long id) { service.delete(id); }

The 4xx/5xx split is the one that matters operationally: 4xx means the client must change something, 5xx means a retry may succeed.

The worst pattern in REST

Returning 200 OK with {"success": false, "error": "..."}. Every client, proxy, retry policy, circuit breaker and monitoring dashboard reads the status code, not your body. A 200 that means failure silently disables all of them. Fintech angle: a payment endpoint that answers 200 for a declined card breaks every retry and reconciliation job downstream — use 422 (or 402) and a machine-readable code.

8.5 Content negotiation, produces and consumes

Under the hood: the five steps

(1) Client states what it wants: Accept: application/json, application/xml;q=0.8. (2) The method narrows what it will emit: produces = APPLICATION_JSON_VALUE. (3) ContentNegotiationManager picks the media type — header strategy by default; optionally ?format=. (4) A matching HttpMessageConverter is selected: MappingJackson2HttpMessageConverter for JSON, Jackson XML / JAXB for XML. (5) The converter writes the body and sets Content-Type. No match → 406.

@GetMapping(value = "/{id}", produces = { MediaType.APPLICATION_JSON_VALUE, MediaType.APPLICATION_XML_VALUE })
public OrderResponse get(@PathVariable Long id) { }

@PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE, produces = MediaType.APPLICATION_JSON_VALUE)
public OrderResponse create(@RequestBody CreateOrderRequest r) { }

@GetMapping(value = "/{id}/invoice", produces = MediaType.APPLICATION_PDF_VALUE)
public byte[] invoice(@PathVariable Long id) { }

Deciding the format from /orders/42.json was deprecated in 5.3 and removed in Spring 6 because it enabled reflected file-download and content-sniffing attacks. Use the Accept header, or a query parameter if you must support browsers.

public class MoneySerializer extends JsonSerializer<Money> {
    @Override public void serialize(Money v, JsonGenerator gen, SerializerProvider p) throws IOException {
        gen.writeStartObject();
        gen.writeStringField("amount", v.amount().toPlainString());     // String, never a JSON number
        gen.writeStringField("currency", v.currency().getCurrencyCode());

Do not declare your own ObjectMapper bean lightly

@Bean ObjectMapper makes JacksonAutoConfiguration back off (@ConditionalOnMissingBean, Phase 2) and you silently lose the JavaTimeModule, the Jdk8Module, your spring.jackson.* properties and any modules other starters registered. The usual symptom: Instant suddenly serialising as a numeric timestamp. Use the customizer.

Fintech: money in JSON

Never let BigDecimal become a JSON number that a JavaScript client parses as a double. Serialise amounts as strings ("19.99") or as minor units (1999 + currency), and read them back with @JsonFormat(shape = STRING) or a custom deserialiser. 0.1 + 0.2 is the interview example.

8.7 DTOs vs entities

The most common structural mistake in Spring codebases

Returning a JPA entity from a controller saves ten minutes on day one and costs considerably more later. Three shapes for three concerns: HTTP edge CreateOrderRequest / OrderResponse shaped by the API contract → domain Order shaped by business rules → persistence OrderEntity shaped by the schema. They look identical on day one and diverge permanently by month three.

ProblemWhat actually happens
Your schema becomes your APIRenaming a column is now a breaking change for every client
Lazy loading explodesJackson touches a lazy association outside the persistence context → LazyInitializationException; or open-in-view masks it and you ship N+1 queries
Infinite recursionBidirectional @OneToMany/@ManyToOne serialises until the stack overflows; @JsonBackReference is a plaster

Safe vs idempotent — a genuinely common mid-level question

Safe = changes nothing. Idempotent = repeating leaves the same state as once. These decide whether a client, proxy or retry policy may repeat a request.

VerbSafeIdempotentMeaning
GET / HEADYesYesRead only
PUTNoYesReplace the whole resource; five times = once
DELETENoYesAlready deleted is still deleted; return 204 both times
POSTNoNoCreates something new each call — why double-clicks create duplicate orders
PATCHNoNot necessarily{"qty": 5} is idempotent; {"qty": "+1"} is not
Making POST safe to retry — the Idempotency-Key

Accept an Idempotency-Key header. Store the key with the result of the first successful call; on a repeat, return the stored response instead of creating a second resource. This is how Stripe and every serious payments API handle network retries — mentioning it signals production experience, and in a fintech interview it is close to mandatory.

@PostMapping
public ResponseEntity<OrderResponse> create(
        @RequestHeader(value = "Idempotency-Key", required = false) String key,
        @RequestBody @Valid CreateOrderRequest request) {
    if (key != null) {
        Optional<OrderResponse> existing = idempotencyStore.find(key);
        if (existing.isPresent()) return ResponseEntity.ok(existing.get());   // no second order
    }
    OrderResponse created = service.create(request);
    if (key != null) idempotencyStore.save(key, created);
    return ResponseEntity.created(location(created)).body(created);
}

Production details the snippet skips: scope the key per client, store it atomically with the write (same transaction, or a unique index on the key), give it a TTL (24 h is common), and return 409 or 422 if the same key arrives with a different payload.

8.9 Pagination, sorting and filtering

Any collection endpoint that can grow must be paginated from day one. Retrofitting it is a breaking change for every client.

@GetMapping
public Page<OrderResponse> list(
        @RequestParam(required = false) OrderStatus status,
        @RequestParam(required = false) @DateTimeFormat(iso = ISO.DATE) LocalDate from,
        @PageableDefault(size = 20, sort = "createdAt", direction = Sort.Direction.DESC) Pageable pageable) {
    return service.search(status, from, pageable).map(OrderResponse::from);
}

Without max-page-size, ?size=1000000 is a one-line denial of service that loads your whole table into memory. It is trivially discoverable and it will be found. Cap it in configuration, not in a comment.

Page vs Slice

Page<T> runs an extra COUNT(*) to fill totalElements; on a large table that count can cost more than the page. If the UI only needs a "next" button, return Slice<T>, which fetches size + 1 rows and skips the count.

8.10 File upload and download

@PostMapping(path = "/{id}/attachments", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
public ResponseEntity<AttachmentResponse> upload(@PathVariable Long id,
        @RequestPart("file") MultipartFile file,
        @RequestPart("meta") @Valid AttachmentMeta meta) {

@GetMapping("/{id}/invoice")
public ResponseEntity<Resource> download(@PathVariable Long id) {

8.11 CORS

Core concept

The browser's same-origin policy blocks a page on one origin from reading a response from another. CORS is the server's way of opting in. For non-simple requests (in practice every JSON API call) the browser first sends a preflight OPTIONS /api/orders with Origin; the server answers with Access-Control-Allow-Origin / -Methods / -Headers / Max-Age; only then does the real request go.

// per-controller
@CrossOrigin(origins = "https://app.example.com", maxAge = 3600)
@RestController public class OrderController { }

// global - the usual choice
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins("https://app.example.com")   // NOT "*" with credentials
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*")
                .exposedHeaders("X-Total-Count")             // readable by JS
                .allowCredentials(true)
                .maxAge(3600);                                // cache the preflight
    }
}
CORS is not security

It is enforced by the browser, not your server. curl, Postman and any server-side client ignore it completely. A permissive policy does not let an attacker in — but it does let a malicious site read authenticated responses in a victim's browser. Authorisation still has to be done server-side.

allowCredentials(true) with allowedOrigins("*")

Rejected by the specification; Spring throws at startup. Use allowedOriginPatterns if you need wildcards with credentials — and think carefully, because any matching site can then make authenticated calls on the user's behalf.

With Spring Security on the classpath

The security filter chain runs before Spring MVC. Enable http.cors(Customizer.withDefaults()) so the CorsConfigurationSource is applied there too — otherwise the preflight OPTIONS is rejected with a 401 before your CORS config is ever consulted.

Version less often than you think — the tolerant reader

A new version is expensive: two code paths, two test suites, two sets of docs, and a client migration to chase. Not breaking: adding an optional response field (if clients ignore unknown fields), a new optional parameter, a new endpoint. Breaking: renaming or removing a field, changing a type or format, making an optional field required, changing the meaning of a status code. Configure your own clients with @JsonIgnoreProperties(ignoreUnknown = true) — Boot's default — and additive changes stop being breaking changes.

9.2 @Valid and @Validated

Under the hood: where validation sits

(1) Body arrives as raw bytes. (2) Jackson deserialises into the DTO — malformed JSON → HttpMessageNotReadableException → 400. (3) @Valid triggers Hibernate Validator, which walks every constraint on the object graph. (4) Violations are collected, not thrown one at a time — the user gets all errors in one response. (5) MethodArgumentNotValidException is raised, carrying a BindingResult with field, rejected value and message. (6) Your @RestControllerAdvice converts it to your error shape — otherwise Boot emits its default 400 body. Validation runs after deserialisation and before your method body.

The 500 that should be a 400

@Validated on parameters throws ConstraintViolationException, which Spring does not map to a status code — a client sending ?size=500 gets a 500 and your error-rate alarms fire for a client mistake. Handle it explicitly in your advice. Spring 6.1 added HandlerMethodValidationException (mapped to 400 when a controller's @Constraints on parameters are validated by the built-in HandlerMethodValidator and the class has no @Validated), but most codebases still rely on the older path.

Phase 2 echo: @Validated at class level makes Spring create a proxy for the controller (MethodValidationPostProcessor). Harmless here, but it is the same mechanism as everywhere else — self-invocation bypasses it, and a final controller class cannot be proxied.

9.3 Nested and collection validation

Validation does not recurse automatically. Without @Valid on the field, Spring checks that the object is non-null and stops there.

9.4 Custom validators

Two pieces: an annotation, and a ConstraintValidator that implements it. Worth doing whenever the same rule appears in more than one DTO.

// the annotation
@Documented
@Constraint(validatedBy = SkuExistsValidator.class)
@Target({ ElementType.FIELD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
public @interface SkuExists {
    String message() default "no product exists with this SKU";
    Class<?>[] groups() default {};                        // required by the spec
    Class<? extends Payload>[] payload() default {};       // required by the spec
}

// the validator - a Spring bean, so DI works
@Component
public class SkuExistsValidator implements ConstraintValidator<SkuExists, String> {
    private final ProductRepository products;
    public SkuExistsValidator(ProductRepository products) { this.products = products; }

    @Override public boolean isValid(String sku, ConstraintValidatorContext ctx) {
        if (sku == null) return true;                         // let @NotNull own null
        return products.existsBySku(sku);
    }
}
Let each constraint do one job

Returning true for null is the convention, not an oversight. It keeps constraints composable: @NotNull @SkuExists reads clearly and produces two distinct messages. A validator that also null-checks produces confusing duplicates.

// class-level validation, for rules that span fields
@Documented @Constraint(validatedBy = DateRangeValidator.class)
@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)          // on the CLASS
public @interface ValidDateRange {
    String message() default "endDate must be after startDate";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class DateRangeValidator implements ConstraintValidator<ValidDateRange, ReportRequest> {
    @Override public boolean isValid(ReportRequest r, ConstraintValidatorContext ctx) {
        if (r.startDate() == null || r.endDate() == null) return true;
        if (!r.endDate().isAfter(r.startDate())) {
            ctx.disableDefaultConstraintViolation();
            ctx.buildConstraintViolationWithTemplate(ctx.getDefaultConstraintMessageTemplate())
               .addPropertyNode("endDate")                                // attach it to a FIELD
               .addConstraintViolation();
            return false;
        }
        return true;
    }
}
Be careful with database calls in validators

@SkuExists issues a query per element. On a request with fifty lines that is fifty round trips before your method body even starts. For collections, prefer a single batch check in the service layer, and keep validators to cheap, self-contained rules.

9.5 Validation groups

The same object often has different rules in different operations: on create, id must be absent; on update, present. Groups express that without duplicating the DTO — and they are the clearest practical reason @Valid and @Validated both exist.

public interface OnCreate { }
public interface OnUpdate { }

public record OrderRequest(
        @Null(groups = OnCreate.class)                       // must be absent when creating
        @NotNull(groups = OnUpdate.class)                    // must be present when updating
        Long id,
        @NotBlank(groups = { OnCreate.class, OnUpdate.class }) String reference,
        @NotNull(groups = OnCreate.class) Long customerId
) { }

@PostMapping
public OrderResponse create(@RequestBody @Validated(OnCreate.class) OrderRequest r) { }
@PutMapping("/{id}")
public OrderResponse update(@PathVariable Long id, @RequestBody @Validated(OnUpdate.class) OrderRequest r) { }
A word of caution

Constraints with no groups belong to the Default group, which is not validated when you name a specific group — a common surprise. And once you have three or more groups on one type, two separate DTOs are usually clearer; separate request types were already recommended in 8.7.

9.6 @ExceptionHandler

Handles exceptions thrown by handler methods. Declared inside a controller it applies to that controller only; declared in a @ControllerAdvice it applies globally.

@RestController
public class OrderController {
    @GetMapping("/{id}")
    public OrderResponse get(@PathVariable Long id) {
        return service.find(id).orElseThrow(() -> new OrderNotFoundException(id));
    }

    @ExceptionHandler(OrderNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handle(OrderNotFoundException e) {
        return new ErrorResponse("ORDER_NOT_FOUND", e.getMessage());
    }
}
  • One method can handle several types: @ExceptionHandler({ A.class, B.class }). If the annotation lists none, the parameter type is used.
  • The most specific match wins — a handler for Exception does not shadow one for OrderNotFoundException.
  • Useful parameters: the exception, HttpServletRequest, WebRequest, HandlerMethod, Locale. Return anything a handler can: a DTO, ResponseEntity, ProblemDetail, or a view name.
Under the hood: the HandlerExceptionResolver chain

throw new OrderNotFoundException(42) anywhere below the controller → the DispatcherServlet catches it and walks the chain in order: (1) ExceptionHandlerExceptionResolver — @ExceptionHandler in the controller, then in @ControllerAdvice beans; where you live. (2) ResponseStatusExceptionResolver — @ResponseStatus on the exception class, and ResponseStatusException. (3) DefaultHandlerExceptionResolver — Spring's own MVC exceptions → 400 / 405 / 415. Nothing handles it → 500 and Boot's BasicErrorController default body.

9.7 @ControllerAdvice and @RestControllerAdvice

A component whose @ExceptionHandler (and @InitBinder, @ModelAttribute) methods apply across controllers. @RestControllerAdvice is @ControllerAdvice + @ResponseBody — the one you want for an API.

@RestControllerAdvice
public class GlobalExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // ---- validation on @RequestBody -------------------------------------------
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ApiError> onInvalidBody(MethodArgumentNotValidException e) {
        List<FieldError> fields = e.getBindingResult().getFieldErrors().stream()
                .map(f -> new FieldError(f.getField(), f.getDefaultMessage())).toList();
        return ResponseEntity.badRequest().body(ApiError.of("VALIDATION_FAILED", "Request validation failed", fields));
    }

    // ---- validation on @RequestParam / @PathVariable ---------------------------
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ApiError> onInvalidParam(ConstraintViolationException e) {
        List<FieldError> fields = e.getConstraintViolations().stream()
                .map(v -> new FieldError(v.getPropertyPath().toString(), v.getMessage())).toList();
        return ResponseEntity.badRequest().body(ApiError.of("VALIDATION_FAILED", "Invalid parameter", fields));
    }

    // ---- your own domain exceptions --------------------------------------------
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ApiError> onNotFound(ResourceNotFoundException e) {
        return ResponseEntity.status(NOT_FOUND).body(ApiError.of(e.code(), e.getMessage(), List.of()));
    }
    @ExceptionHandler(BusinessRuleException.class)
    public ResponseEntity<ApiError> onBusinessRule(BusinessRuleException e) {
        return ResponseEntity.unprocessableEntity().body(ApiError.of(e.code(), e.getMessage(), List.of())); // 422
    }

    // ---- the safety net ----------------------------------------------------------
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ApiError> onUnexpected(Exception e, HttpServletRequest req) {
        String id = UUID.randomUUID().toString();
        log.error("unhandled [{}] {} {}", id, req.getMethod(), req.getRequestURI(), e);   // full trace in the LOG
        return ResponseEntity.status(INTERNAL_SERVER_ERROR)
                .body(ApiError.of("INTERNAL_ERROR", "Unexpected error. Quote reference " + id, List.of()));
    }
}
Never leak a stack trace to the client

The catch-all logs the full exception with a generated reference and returns only that reference. Stack traces disclose framework versions, package structure, SQL and sometimes data — free reconnaissance for an attacker, meaningless to a legitimate client. The reference id is what makes support tractable. In a regulated fintech context, leaking internals is an audit finding.

9.8 Designing an exception hierarchy

The goal is that the advice in 9.7 stays short and stable as the application grows: a small number of base types that map cleanly onto status codes.

public abstract class ApiException extends RuntimeException {
    private final String code;                          // stable, machine-readable
    protected ApiException(String code, String message) { super(message); this.code = code; }
    protected ApiException(String code, String message, Throwable cause) { super(message, cause); this.code = code; }
    public String code() { return code; }
}

public class ResourceNotFoundException extends ApiException {           // -> 404
    public ResourceNotFoundException(String resource, Object id) {
        super(resource.toUpperCase() + "_NOT_FOUND", resource + " " + id + " not found");
    }
}
public class BusinessRuleException extends ApiException { /* -> 422 */ public BusinessRuleException(String code, String msg) { super(code, msg); } }
public class ConflictException     extends ApiException { /* -> 409 */ public ConflictException(String code, String msg) { super(code, msg); } }
public class UpstreamException     extends ApiException {  // -> 502 / 504
    public UpstreamException(String service, Throwable cause) { super("UPSTREAM_UNAVAILABLE", service + " is unavailable", cause); }
}
DecisionRecommendation
Checked or unchecked?Unchecked. Checked exceptions force every layer to declare or wrap them, and Spring only rolls a transaction back on unchecked exceptions by default (Phase 4)
How many types?One base plus four or five subtypes: 404, 409, 422, 401/403, upstream. A class per business rule bloats the advice — use the code field for that
Message wordingWritten for the caller, not the developer. No SQL, no internal ids, no class names
Machine-readable codeEssential. Clients branch on ORDER_ALREADY_PAID, never on an English message that translation or a copy edit will change
Why not @ResponseStatus on the exception class?

It works and is briefly tempting, but it hard-codes an HTTP concept into a domain class and gives no control over the body. Keeping the mapping in the advice leaves domain exceptions transport-agnostic — the same ones can be reused from a Kafka listener or a batch job.

Every error your API returns should have the same shape. Clients write one parser and one error path; without it, every endpoint is a small integration project.

10Filters, interceptors & the request lifecycle

Everything that happens before and after your method runs — and the full path from socket to response. If you can narrate the ten stages in 10.8 and say which layer each concern belongs to, you can answer most Spring MVC interview questions, because nearly all of them are asking about one stage of it.

10.1 Servlet filters

Core concept

A Filter is Servlet API, not Spring. It sits outside the DispatcherServlet and sees every request into the container — static resources, Actuator endpoints, and requests that never match a controller at all. Spring Security is entirely filters.

@Component
@Order(1)
public class RequestTimingFilter implements Filter {
    private static final Logger log = LoggerFactory.getLogger(RequestTimingFilter.class);

    @Override public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        long start = System.nanoTime();
        try {
            chain.doFilter(req, res);                                    // pass it down the chain
        } finally {                                                      // ALWAYS measure / restore here
            long ms = (System.nanoTime() - start) / 1_000_000;
            log.info("{} {} -> {} ({} ms)", ((HttpServletRequest) req).getMethod(),
                     ((HttpServletRequest) req).getRequestURI(), ((HttpServletResponse) res).getStatus(), ms);
        }
    }
}
Forgetting chain.doFilter()

If you do not call it, the request stops dead — no controller, and usually an empty 200 with no explanation. The single most common filter bug, easy to cause by returning early from a guard clause.

Extend OncePerRequestFilter

Runs once per request even when the request is forwarded or dispatched asynchronously, and hands you typed HttpServletRequest/HttpServletResponse so you can drop the casts. shouldNotFilter() gives a clean exclusion hook.

@Component
public class ApiKeyFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = req.getHeader("X-API-Key");
        if (key == null || !keyService.isValid(key)) {
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            res.setContentType("application/json");
            res.getWriter().write("{\"code\":\"INVALID_API_KEY\"}");
            return;                                                  // deliberately no chain.doFilter
        }
        chain.doFilter(req, res);
    }
    @Override protected boolean shouldNotFilter(HttpServletRequest req) {
        return req.getRequestURI().startsWith("/actuator/health");
    }
}

10.2 HandlerInterceptor

Core concept

A Spring MVC concept. It runs inside the DispatcherServlet, after the handler has been resolved — so unlike a filter it knows which controller method is about to run and can read its annotations. Three hooks: preHandle() before the handler (return false → stop); postHandle() after the handler — skipped if it threw; afterCompletion() after the response — always runs, receives the exception.

@Component
public class AuditInterceptor implements HandlerInterceptor {
    @Override public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        if (handler instanceof HandlerMethod hm) {
            Audited audited = hm.getMethodAnnotation(Audited.class);      // sees annotations
            if (audited != null) req.setAttribute("auditAction", audited.value());
        }
        return true;                                                     // false -> stop; nothing below runs
    }
    @Override public void postHandle(HttpServletRequest req, HttpServletResponse res, Object handler, ModelAndView mav) {
        // NOT called if the handler threw
    }
    @Override public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        // ALWAYS called - cleanup here; note it receives the exception
        auditService.record((String) req.getAttribute("auditAction"), res.getStatus(), ex);
    }
}

// registration - interceptors are NOT picked up automatically
@Configuration
public class WebConfig implements WebMvcConfigurer {
    private final AuditInterceptor auditInterceptor;
    public WebConfig(AuditInterceptor auditInterceptor) { this.auditInterceptor = auditInterceptor; }

    @Override public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(auditInterceptor)
                .addPathPatterns("/api/**")
                .excludePathPatterns("/api/health", "/api/public/**")
                .order(1);
    }
}
Put cleanup in afterCompletion(), never in postHandle()

If the handler throws, postHandle() never runs — an MDC value or open resource set in preHandle() would leak. And preHandle returning false stops the request with no controller and no postHandle; afterCompletion still runs for interceptors whose preHandle already succeeded. You must write the response yourself before returning false, otherwise the client gets an empty 200.

10.5 Request and response logging

Harder than it looks, for one reason: the request body is an input stream that can only be read once. If a filter reads it to log it, the controller receives an empty body — surfacing as a confusing HttpMessageNotReadableException or a DTO with all-null fields.

    CommonsRequestLoggingFilter f = new CommonsRequestLoggingFilter();
    f.setIncludeQueryString(true); f.setIncludePayload(true); f.setMaxPayloadLength(2048); f.setIncludeHeaders(false);
    return f;
}
// plus: logging.level.org.springframework.web.filter.CommonsRequestLoggingFilter=DEBUG
The proper approach — content-caching wrappers 
@Component @Order(-90)
public class PayloadLoggingFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        ContentCachingRequestWrapper  wreq = new ContentCachingRequestWrapper(req);
        ContentCachingResponseWrapper wres = new ContentCachingResponseWrapper(res);
        try {
            chain.doFilter(wreq, wres);                             // downstream reads normally
        } finally {
            log.info("{} {} <- {}", req.getMethod(), req.getRequestURI(), truncate(wreq.getContentAsByteArray()));
            log.info("{} -> {}", wres.getStatus(), truncate(wres.getContentAsByteArray()));
            wres.copyBodyToResponse();                              // MANDATORY - or the client gets nothing
        }
    }
}
copyBodyToResponse() is not optional

ContentCachingResponseWrapper buffers the response so you can read it. Forget the final copyBodyToResponse() and the body stays in the buffer: the client receives an empty response with the right status code — maddening, because everything else looks correct.

What not to log

Never log full bodies in production by default. Passwords, tokens, card numbers (PAN) and personal data end up in your log aggregator, which is usually far more widely readable than your database — and logging a full PAN is a PCI-DSS violation on its own. Mask known-sensitive fields, or log only on a sampled basis, or only for 4xx/5xx. Cap the logged size. Prefer structured logging: method, path, status, duration, trace id as separate fields.

10.6 Correlation IDs and trace propagation

One user action crosses several services and produces log lines on each. Without a shared identifier, reconstructing what happened is guesswork. A correlation id is the cheapest high-value thing you can add to a service.

@Component @Order(-100)                                          // before anything that logs
public class CorrelationIdFilter extends OncePerRequestFilter {
    public static final String HEADER = "X-Correlation-Id";
    public static final String MDC_KEY = "traceId";

    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader(HEADER)).filter(s -> !s.isBlank())
                            .orElseGet(() -> UUID.randomUUID().toString());
        try {
            MDC.put(MDC_KEY, id);                                   // now every log line carries it
            res.setHeader(HEADER, id);                              // and the client gets it back
            chain.doFilter(req, res);
        } finally {
            MDC.remove(MDC_KEY);                                    // MANDATORY - threads are pooled
        }
    }
}

# %X pulls values out of the MDC
logging.pattern.console: "%d{HH:mm:ss} %-5level [%X{traceId:-}] %logger{20} - %msg%n"

// propagating to downstream calls
@Bean RestClientCustomizer correlationPropagation() {
    return builder -> builder.requestInterceptor((request, body, execution) -> {
        String id = MDC.get(CorrelationIdFilter.MDC_KEY);
        if (id != null) request.getHeaders().add(CorrelationIdFilter.HEADER, id);
        return execution.execute(request, body);
    });
}
Always clear the MDC

The MDC is a ThreadLocal, and Tomcat pools its threads. Leave a value behind and the next request served by that thread inherits it — log lines stamped with another user's trace id, both confusing and a privacy problem. The finally block is not optional. (Same reason @Async and virtual-thread executors need a task decorator to copy the MDC across.)

Consider Micrometer Tracing instead of hand-rolling

spring-boot-starter-actuator + micrometer-tracing-bridge-brave (or -otel) gives W3C-standard traceparent propagation, automatic instrumentation of RestClient, WebClient, JDBC and Kafka, and MDC keys traceId/spanId populated for you. Hand-rolling is fine for one service; across many, use the standard. Return the id in the error response too — the traceId in ApiError (9.9) is exactly this value.

10.7 HandlerMethodArgumentResolver

Core concept

The machinery behind @PathVariable, @RequestBody and the rest: supportsParameter() decides whether it applies, resolveArgument() produces the value. Writing your own removes repetitive boilerplate — pulling the current user out of the security context, or a tenant out of a header, in forty controller methods.

@Target(ElementType.PARAMETER) @Retention(RetentionPolicy.RUNTIME)
public @interface CurrentUser { }

@Component
public class CurrentUserArgumentResolver implements HandlerMethodArgumentResolver {
    private final UserService users;
    public CurrentUserArgumentResolver(UserService users) { this.users = users; }

    @Override public boolean supportsParameter(MethodParameter p) {
        return p.hasParameterAnnotation(CurrentUser.class) && p.getParameterType().equals(AuthenticatedUser.class);
    }
    @Override public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                                            NativeWebRequest request, WebDataBinderFactory binder) {
        String userId = request.getHeader("X-User-Id");
        if (userId == null) throw new UnauthorizedException("missing user");
        return users.load(userId);
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    private final CurrentUserArgumentResolver resolver;
    public WebConfig(CurrentUserArgumentResolver resolver) { this.resolver = resolver; }
    @Override public void addArgumentResolvers(List<HandlerMethodArgumentResolver> resolvers) { resolvers.add(resolver); }
}

// what every controller method looks like afterwards
@GetMapping("/me/orders")
public List<OrderResponse> myOrders(@CurrentUser AuthenticatedUser user) {
    return service.findByCustomer(user.id());                   // no boilerplate, and testable
}
Why this beats a ThreadLocal helper

A static CurrentUserHolder.get() works, but hides the dependency, makes the method untestable without setting up thread state, and leaks across pooled threads if not cleared. An argument resolver makes the dependency an explicit parameter — the unit test just passes one in. The mirror image is HandlerMethodReturnValueHandler, which decides what to do with what you return; @ResponseBody is implemented by one of these. (With Spring Security, @AuthenticationPrincipal is exactly such a resolver, already written.)

10.8 The complete request lifecycle

Socket to socket — the ten stages
  1. Connector accepts the socket, a worker thread is assigned — Tomcat NIO; one thread per request, default pool of 200.
  2. Filter chain runs, in @Order sequence — encoding · correlation id · Spring Security · your filters.
  3. DispatcherServlet receives the request — mapped to /; the front controller.
  4. HandlerMapping resolves the handler method — path, method, headers, params, consumes, produces.
  5. Interceptor preHandle() runs, in order — returning false short-circuits everything below.
  6. Argument resolvers build the parameters — @PathVariable · @RequestParam · @RequestBody + Jackson · @Valid.
  7. AOP proxies wrap the call — @Transactional opens the transaction at the service proxy, not in the controller.
  8. Your controller method executes — returns an object, a ResponseEntity, or throws.
  9. Return-value handler + HttpMessageConverter write the body — or a HandlerExceptionResolver produces the error response instead.
  10. Interceptor postHandle(), then afterCompletion(), then filters unwind — response flushed, thread returned to the pool.

The thread model, and why it matters

Stages 2 to 10 all run on one container thread, held for the entire request. Tomcat's default pool is 200. If your controller blocks for two seconds on a slow upstream call, that thread is unavailable for two seconds — 200 concurrent slow requests saturate the server and everything queues. This is the limitation that @Async, CompletableFuture, WebFlux and now virtual threads (spring.threads.virtual.enabled=true on Java 21, Boot 3.2+) exist to address. It is also why ThreadLocal state must always be cleared: the thread goes straight back into the pool for someone else's request.

A good closing answer

"A request arrives on a pooled container thread, passes through the servlet filter chain, reaches the DispatcherServlet, which uses HandlerMapping to find the controller method and HandlerAdapter to invoke it. Argument resolvers deserialise and validate the input, AOP proxies wrap the service call so the transaction opens there, the return value goes through an HttpMessageConverter, and anything thrown is caught by a HandlerExceptionResolver and turned into a response by my @RestControllerAdvice. Interceptor afterCompletion and the filters' finally blocks clean up before the thread returns to the pool."

11Most-asked questions

The PDF's 30 for a mid-level role, plus 10 more that fintech interviews add on top. Web-layer questions are where interviewers check whether you have actually run an API or only written one: expect status codes, error consistency, pagination limits and thread exhaustion rather than annotation trivia. every round common senior

Web layer

@Controller vs @RestController? every round

@RestController is @Controller + @ResponseBody on every method. With @Controller, a returned String is a view name handed to a ViewResolver. With @RestController, the return value is the response body and goes through an HttpMessageConverter. The bug worth mentioning: return a DTO from a plain @Controller and Spring treats toString() as a view name, then fails to find that template — the error talks about views and says nothing about serialisation.

What do @PathVariable, @RequestParam, @RequestBody and @RequestHeader each read? every round

Different parts of the same HTTP message. @PathVariable a segment of the URL path; @RequestParam a query-string parameter or form-encoded field; @RequestBody the body via an HttpMessageConverter, normally Jackson; @RequestHeader a header. @CookieValue and @RequestPart round it out. When missing: a path variable cannot be missing (the mapping would not have matched); the others produce a 400 unless required = false or a defaultValue.

When do you return ResponseEntity instead of the object directly? every round

Whenever you need control over the status code or headers; returning the object gives 200 OK and nothing else. Concretely: 201 Created with a Location header after a POST; 204 after a delete; conditional responses with ETag / Cache-Control; or when the same method returns 200 or 404 depending on the outcome. For "always this status", @ResponseStatus on the method is lighter.

How does a Java object become JSON, and how do you customise it? common

MappingJackson2HttpMessageConverter, registered because Jackson is on the classpath via starter-web; content negotiation picks it from Accept and produces. Per field: @JsonProperty, @JsonIgnore, @JsonFormat, @JsonInclude. Globally: spring.jackson.* or a Jackson2ObjectMapperBuilderCustomizer. The trap: declaring your own @Bean ObjectMapper makes Boot back off entirely — you lose the JavaTimeModule and your properties; symptom is Instant serialising as a number.

Content negotiation — what causes a 406 versus a 415? common

The client proposes media types in Accept; the method constrains with produces; ContentNegotiationManager picks the intersection and a converter writes the body. 415: the request's Content-Type is not in consumes — the server cannot read what you sent. 406: the request's Accept is not in produces — the server cannot write what you asked for. Request side versus response side. Path-extension negotiation (/orders/42.json) was removed in Spring 6.

Is CORS a security mechanism? common

No. It is enforced by the browser. curl, Postman and server-side clients ignore it, so a permissive policy does not let an attacker reach anything new; authorisation must still be server-side. What it prevents is a malicious site reading authenticated responses in a victim's browser. Two practical points: allowCredentials(true) with allowedOrigins("*") fails at startup; and with Spring Security you must enable http.cors(), because the security chain runs before MVC and would otherwise reject the preflight OPTIONS with a 401.

Two controller methods map to the same path. What happens? common

The application fails to start with IllegalStateException: Ambiguous mapping naming both methods, because RequestMappingHandlerMapping builds its table during context refresh — a startup failure, which is the desirable behaviour. Only ambiguous if nothing distinguishes them: mappings also match on HTTP method, params, headers, consumes, produces, so the same path is legal when one takes JSON and the other multipart.

What changed in Spring 6 / Boot 3 that breaks an old web app? senior

Four that bite: javax.* → jakarta.* (every servlet, filter, validation import); trailing-slash matching removed in 6.1 (/orders/ now 404s); path-extension content negotiation removed; and spring-boot-starter-validation no longer transitively present (since 2.3, but people upgrading from 2.2 notice now). Plus Springfox is dead — move to springdoc. Bonus: PathPatternParser is the default matcher, which is faster but rejects some AntPathMatcher patterns with ** in the middle.

REST design

Status code for: created, deleted, not logged in, logged in but not allowed, duplicate, failed business rule? every round

201 + Location for created. 204 for a delete with nothing to return. 401 not authenticated. 403 authenticated but not authorised — this pair is confused constantly. 409 duplicate or version conflict. 422 syntactically valid input that violates a business rule, keeping 400 for malformed syntax and validation failures. The anti-pattern worth naming: 200 OK with {"success": false} — every proxy, retry policy, circuit breaker and dashboard reads the status code, so a 200 that means failure disables all of them.

Which HTTP methods are idempotent, and why does it matter? every round

GET, HEAD, PUT, DELETE are idempotent — repeating leaves the same state. GET/HEAD are also safe. POST is neither; PATCH depends on the payload ({"qty": 5} yes, {"qty": "+1"} no). It matters because idempotency is what lets a client, proxy or retry policy safely repeat a request after a timeout. For POST, you get the same guarantee with an Idempotency-Key header: store the first result, replay it on a repeat — how payment APIs avoid double-charging on a network retry.

Why not return JPA entities from a controller? every round

Five reasons; any two make the case. Your schema becomes your public API (column rename = breaking change). Lazy associations throw LazyInitializationException during serialisation or, with open-in-view, quietly emit N+1 queries. Bidirectional relationships recurse until the stack overflows. New fields leak automatically — add passwordHash and it is in the API that day. And accepting an entity as @RequestBody allows mass assignment of id, version, role. Use separate request and response records; map with a static factory or MapStruct.

How do you paginate a collection endpoint? every round

Accept a Pageable with @PageableDefault, return Page<T>; Spring Data binds page, size and repeated sort. Always mention two things: cap the page size with spring.data.web.pageable.max-page-size — without it ?size=1000000 is a one-line DoS; and use Slice<T> when the UI only needs "next", because Page runs an extra COUNT(*). For deep pagination or feeds, offset degrades and rows shift under concurrent inserts — keyset/cursor pagination is constant-time and stable.

How do you version an API, and when should you? common

Four options: URI path (/api/v2/orders), query parameter, custom header, or content negotiation with a vendor media type. URI is the least REST-pure and by far the most shipped: visible, cacheable, routable at a gateway. The better half of the answer is when: adding an optional field, parameter or endpoint is not breaking if clients ignore unknown fields (Boot's Jackson default); renaming/removing a field, changing a type, or making optional required is. Configure clients as tolerant readers and you version far less often — each version is two code paths, two test suites and a migration to chase.

How would you make a "transfer money" POST safe against a client retry? senior fintech

Idempotency-Key header, required (not optional) for money-moving endpoints. On arrival: look up the key scoped to the client; if present and the payload hash matches, return the stored response (same status, same body); if present with a different payload, 422 IDEMPOTENCY_KEY_REUSED; if absent, reserve the key in the same transaction as the transfer (unique index on (client_id, key)) so two concurrent identical requests cannot both proceed — the second hits the unique violation and waits/replays. TTL the keys (24 h). Also return 202 if the transfer is asynchronous and give a status resource to poll.

Should a controller be @Transactional? common

No. The transaction belongs at the service boundary, where one unit of business work begins and ends. On the controller it stretches across serialisation, validation and response writing, holding a DB connection longer than necessary and shrinking your effective pool; it encourages open-in-view-style lazy loading during serialisation (N+1 you never see in a unit test); and it makes the controller do two jobs. Stage 7 of the lifecycle: the proxy wraps the service call, not the controller.

What would you put in a code-review checklist for a new REST endpoint? senior

DTOs not entities, both directions. Collection endpoint paginated with a capped size. Status codes right: 201 + Location, 204 for delete, 422 not 400 for business rules. Input validated with @Valid including nested objects and collection elements. Errors through the global advice, standard shape, no stack trace. Nothing logged that should not be. Idempotent, or an Idempotency-Key. Documented — springdoc mostly does it if validation annotations are right. And the one people forget: transaction at the service layer, not the controller.

Validation

@NotNull, @NotEmpty, @NotBlank — differences? every round

@NotNull only checks null. @NotEmpty is not-null and size > 0, for String, collections, maps, arrays. @NotBlank is String-only and requires a non-whitespace character. For " ": @NotNull passes, @NotEmpty passes (length 2), @NotBlank fails.

@Valid vs @Validated? every round

@Valid is the Jakarta standard and cascades into nested objects. @Validated is Spring's and adds validation groups and class-level support for constraints directly on @RequestParam/@PathVariable. The difference that bites: @Valid on a body throws MethodArgumentNotValidException → 400; @Validated on a parameter throws ConstraintViolationException, which is not mapped — an invalid ?size=500 returns a 500 unless your advice handles it.

How do you validate a list of nested objects? common

Validation does not recurse by default. @Valid on the field to descend into an object, and on the element type for a collection: List<@Valid OrderLine> lines, not @Valid List<OrderLine> — the second does nothing useful. The payoff is the field paths you get back: lines[0].quantity, shippingAddress.postcode — exactly what lets a front end highlight the right input.

How would you write a custom validation constraint? common

Two pieces: an annotation meta-annotated @Constraint(validatedBy = ...) with the three required members message(), groups(), payload(); and a ConstraintValidator<A, T> implementing isValid. Make it a @Component and DI works, so it can query a repository. Convention: return true for null and let @NotNull own that case. For rules spanning fields, target ElementType.TYPE and attach the violation to a field with addPropertyNode. Caution: a DB-hitting validator runs per element — fifty lines is fifty round trips; batch that in the service.

Validation annotations are on your DTO but nothing is being validated. Why? common

One of three. @Valid missing on the @RequestBody parameter — constraints are inert without it. spring-boot-starter-validation not on the classpath — removed from starter-web in Boot 2.3. Or the constraint is on a nested object with no @Valid on the field or element type. Quick check: put @NotBlank on a top-level field and post an empty value; if that fails correctly the problem is cascading, if not it is the starter or the missing @Valid.

How do you validate a money amount properly? senior fintech

Type is BigDecimal, never double. Constraints: @NotNull, @DecimalMin("0.01") (or @Positive), @Digits(integer = 12, fraction = 2) — and the fraction limit is currency-dependent (JPY has 0, BHD has 3), so the real check is a class-level constraint that reads the currency field. Deserialise from a JSON string to avoid double parsing on the wire. And @Min/@Max do not apply to BigDecimal the way people think — use the @Decimal* forms.

Error handling

How do you handle exceptions globally in a Spring Boot API? every round

A single @RestControllerAdvice with @ExceptionHandler methods. The resolver chain runs ExceptionHandlerExceptionResolver first, and within it a controller-local handler beats a global one — worth knowing when a global handler mysteriously does not fire. Contents: handlers for MethodArgumentNotValidException and ConstraintViolationException → 400; a small domain hierarchy → 404/409/422; and a catch-all for Exception that logs the full trace with a generated reference and returns only that id.

How would you design an exception hierarchy? common

One abstract ApiException extends RuntimeException carrying a stable machine-readable code, plus four or five subtypes mapping to status codes: not-found, conflict, business-rule, unauthorised, upstream-failure. Unchecked: checked exceptions force every layer to declare or wrap them, and Spring only rolls back on unchecked by default. No @ResponseStatus on the classes — it hard-codes HTTP into a domain type and gives no control over the body; keeping the mapping in the advice means the same exceptions work from a Kafka listener or batch job.

What does a good error response look like? every round

The same shape for every error, including 500s. A machine-readable code clients branch on; a human-readable message safe to display; an errors array of field/message pairs, empty when not applicable; timestamp, path, and a traceId. Return all validation errors at once. The traceId is the highest-value field: a user quotes it, you find the request. For new APIs use ProblemDetail (RFC 9457), native in Spring 6, extended with code and traceId.

What is ProblemDetail and how does it relate to ResponseEntityExceptionHandler? senior

ProblemDetail is Spring 6's model of RFC 7807/9457: type, title, status, detail, instance + extension properties, written as application/problem+json. ResponseEntityExceptionHandler is a base class for your advice that already handles every built-in MVC exception (404, 405, 415, unreadable body, invalid argument) — extend it and override handleMethodArgumentNotValid etc. to add your field errors. spring.mvc.problemdetails.enabled=true switches Boot's own error responses to the format even without an advice.

A client sees "Internal Server Error" with a stack trace in the body. What is wrong and how do you fix it? common

Either no catch-all advice exists and server.error.include-stacktrace is always (or a dev profile leaked to prod), or a handler is rethrowing. Fix: a catch-all @ExceptionHandler(Exception.class) that logs the trace with a reference id and returns only the id; server.error.include-stacktrace=never, include-message=never, include-binding-errors=never in prod; whitelabel.enabled=false. In fintech this is an audit finding, not a nicety: stack traces expose framework versions, SQL and package structure.

Lifecycle

Filter or interceptor — how do you choose? every round

A filter is Servlet API, outside the DispatcherServlet: sees every request including static resources and 404s, and can wrap the raw streams. An interceptor is Spring MVC, after the handler is resolved: knows which controller method was chosen and can read its annotations. The deciding test: needs the raw request or must run for requests that never reach a controller → filter (auth, CORS, compression, correlation ids, rate limiting). Needs to know which handler → interceptor. Needs the resolved arguments or must work from a scheduler or listener → AOP aspect.

The three HandlerInterceptor methods and when each runs? common

preHandle before the handler — returning false stops everything below and you must write the response yourself or the client gets an empty 200. postHandle after the handler, only if it did not throw. afterCompletion always, after the response, and it receives the exception. The rule: cleanup goes in afterCompletion, never postHandle.

Why can't you just read the request body in a filter to log it? common

The body is an InputStream that can be read once. Consume it in a filter and the controller gets an empty body — a confusing HttpMessageNotReadableException or a DTO with all-null fields. Fix: ContentCachingRequestWrapper / ContentCachingResponseWrapper, which buffer so it can be read twice; and you must call copyBodyToResponse() in a finally or the client gets an empty response with the correct status. And do not log full bodies in production by default.

How do you register a filter, and what is the double-registration bug? common

Three ways: @Component + @Order (always /*); FilterRegistrationBean (URL patterns and order); @WebFilter + @ServletComponentScan (no ordering, no DI). The bug: @Component on the class and a FilterRegistrationBean for it registers it twice — once at /*, once with your patterns — so it runs twice per request; silently wrong for a counting, auditing or rate-limiting filter. Drop the @Component or disable the auto-registration.

How would you implement correlation IDs? common

A OncePerRequestFilter ordered early, before anything that logs. Read an incoming X-Correlation-Id or generate a UUID, put it in the SLF4J MDC, echo it on the response, propagate on outbound calls with a RestClient interceptor, add %X{traceId} to the log pattern. The critical detail: clear the MDC in a finally block — it is a ThreadLocal and Tomcat pools threads, so a leftover value is inherited by the next request. Across services, use Micrometer Tracing: W3C traceparent and automatic instrumentation.

What is a HandlerMethodArgumentResolver and why would you write one? senior

The mechanism behind @PathVariable, @RequestBody and every parameter annotation: supportsParameter decides whether it applies, resolveArgument produces the value. You write one to remove repetition — the current user or tenant in forty controller methods becomes a @CurrentUser parameter. It beats a static ThreadLocal helper because the dependency is an explicit parameter the unit test just passes in, and there is nothing to leak across pooled threads.

Walk me through the complete lifecycle of a request in Spring Boot. every round

Tomcat accepts the socket on a pooled worker thread. The filter chain runs in order — encoding, correlation id, Spring Security. DispatcherServlet on /. HandlerMapping resolves the method from path, verb, headers and media types. Interceptor preHandle. HandlerAdapter invokes the method: argument resolvers deserialise via Jackson and run Bean Validation. AOP proxies wrap the service call, so the transaction opens there. Return value through an HttpMessageConverter; anything thrown to a HandlerExceptionResolver and then my advice. postHandle, afterCompletion, filters unwind, thread back to the pool. Add: all on one thread, default pool 200 — 200 slow calls saturate the server; that is what @Async, WebFlux and virtual threads address.

A client reports an empty body with status 200. Where do you look? common

Three usual suspects, in order: a filter that did not call chain.doFilter() (a guard clause returning early); a ContentCachingResponseWrapper without copyBodyToResponse(); an interceptor preHandle returning false without writing a response. All three share a shape: something short-circuited and the status looks healthy, so the logs give no hint. A timing filter at the very outside of the chain logging method, path, status and duration makes this class of bug visible immediately.

What does spring.threads.virtual.enabled do to this lifecycle? senior

On Java 21 with Boot 3.2+, Tomcat's request handling runs on virtual threads instead of the 200-platform-thread pool, so a controller blocking for two seconds on an upstream call no longer holds a scarce OS thread — thread-per-request scales to tens of thousands of concurrent requests without WebFlux. Nothing in the ten stages changes; what changes is the cost of blocking. Caveats: synchronized blocks pin the carrier thread (fixed in Java 24), ThreadLocal-heavy code (MDC) still works but is memory-costlier, and connection pools become the new bottleneck — a thousand virtual threads all waiting on a 10-connection HikariCP pool just wait faster.

How do you rate-limit an endpoint, and at which layer? senior fintech

Filter layer (stage 2), because it must run for every request and before any expensive work; ideally a gateway in front of the app for the coarse limit and a filter for per-client or per-endpoint limits. Token bucket per key (client id, API key, or IP as a fallback) in Redis for a multi-instance deployment (Bucket4j has a Redis backend); an in-memory bucket is fine for one instance. On limit: 429 with Retry-After and X-RateLimit-Remaining, and a consistent error body. Never 503 — that tells load balancers your instance is unhealthy.

How do you test a controller without starting the whole app? common

@WebMvcTest(OrderController.class) loads only the web slice: the controller, your @ControllerAdvice, filters, Jackson, converters — not services or repositories, which you replace with @MockitoBean (Boot 3.4+; @MockBean before). Drive it with MockMvc (or MockMvcTester with AssertJ in Boot 3.4) and assert status, JSON paths and headers. Because the advice is loaded, this is also where you test the error shape and validation paths. Filters and interceptors are included, so a correlation-id filter can be asserted on the response header.

RestTemplate, WebClient or RestClient for calling another service? common

RestClient (Spring 6.1 / Boot 3.2): synchronous, fluent, the modern replacement for RestTemplate, which is in maintenance mode. WebClient is reactive — only if you are on WebFlux or genuinely need non-blocking composition. Whichever you use: set connect and read timeouts (the defaults are infinite in some clients), propagate the correlation id, map 4xx/5xx to your UpstreamException, and put a circuit breaker (Resilience4j) around anything that moves money. Declarative HTTP interfaces (@HttpExchange) sit on top of either.

How would you add audit logging of who changed what on every write endpoint? senior fintech

Not in the controller. A HandlerInterceptor reading an @Audited method annotation captures the endpoint and outcome (afterCompletion has the status and exception); the identity comes from the security context; the correlation id from the MDC. For the "what changed", an AOP aspect or JPA entity listeners (@PrePersist/@PreUpdate, or Envers) on the service/data layer — the interceptor cannot see resolved arguments. Write the audit record in the same transaction as the change or to an append-only outbox; an audit trail that can be lost when the write commits is not an audit trail. Never log the full request body (PAN, secrets).

The filter that swallows requests
@Component

    }
}

Runs; every API call is counted twice, so clients hit the limit at half the quota. @Component auto-registers the filter at /*, and the FilterRegistrationBean registers it again at /api/*. OncePerRequestFilter does not save you here — it dedupes by filter name, and the two registrations have different names. Fix: drop @Component (construct it in the config), or add a second registration bean for the auto-registered instance with setEnabled(false).

The interceptor that leaks on error
public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object h) {
    MDC.put("user", currentUser(req)); return true;
}
public void postHandle(HttpServletRequest req, HttpServletResponse res, Object h, ModelAndView mav) {
    MDC.remove("user");
}

Leaks whenever the handler throws. postHandle is skipped on exception, so the MDC entry survives into the next request on that thread — log lines attributed to the wrong user. Fix: move the remove to afterCompletion, which always runs and receives the exception. (Better still, do MDC work in a filter with try/finally, which also covers requests that never reach a handler.)

The retry that charged twice
@PostMapping("/transfers")
public ResponseEntity<TransferResponse> transfer(@RequestHeader("Idempotency-Key") String key,
                                                 @RequestBody @Valid TransferRequest r) {
    if (store.exists(key)) return ResponseEntity.ok(store.get(key));
    TransferResponse t = service.transfer(r);      // @Transactional
    store.save(key, t);                            // separate table, separate transaction
    return ResponseEntity.created(uri(t)).body(t);
}

Under load: two concurrent requests with the same key both pass the exists check and both transfer. Check-then-act without atomicity. Also, if save fails after the transfer committed, the next retry transfers again. Fix: reserve the key inside the same transaction as the transfer, with a unique constraint on (client, key) so the second insert fails and replays the stored response; compare a payload hash and return 422 on mismatch; and give the replay the same status as the original (201), not 200.

The page size nobody capped
@GetMapping public Page<TxnResponse> list(@RequestParam(defaultValue = "0") int page,
                                        @RequestParam(defaultValue = "20") int size) {
    return repo.findAll(PageRequest.of(page, size)).map(TxnResponse::from);
}

Runs until someone sends ?size=5000000. One request loads the whole transactions table into heap — a one-line DoS, trivially discoverable. Also runs a COUNT(*) per call on a hot table, and offset pagination on a transactions feed skips/repeats rows as inserts land. Fix: Pageable + spring.data.web.pageable.max-page-size=100 (or clamp in code), Slice if no total is needed, keyset pagination by (created_at, id) for the feed.

14Cheat sheet

The sentence that carries the phase

The framework will happily let you do the expedient thing — return the entity, skip pagination, return 200 with an error field, log the whole body — and none of it fails in development. It fails in production, at scale, in front of someone else. Every trap in this phase is a cheap-now, expensive-later decision.

Request lifecycle (10)

Tomcat thread → filter chain in @Order → DispatcherServlet on / → HandlerMapping → interceptors preHandle → argument resolvers (bind, Jackson, @Valid) → AOP proxy (@Transactional at the service) → controller → return-value handler + HttpMessageConverter, or HandlerExceptionResolver → advice → postHandle, afterCompletion, filters unwind, thread to pool.

Which layer

Raw request or every request (auth, CORS, encoding, correlation id, rate limit) → filter · needs the handler method / annotation → interceptor · needs resolved arguments or must work off-web (tx, cache, retry) → aspect.

Status codes

201 + Location created · 204 delete/update with no body · 202 async accepted · 400 malformed / validation · 401 not authenticated · 403 not authorised · 404 · 409 conflict · 415 cannot read your Content-Type · 406 cannot write your Accept · 422 business rule · 429 + Retry-After · 500 with a reference id, never a trace. Never 200 with success:false.

Idempotency

Safe: GET, HEAD. Idempotent: GET, HEAD, PUT, DELETE. Not: POST, PATCH (payload-dependent). POST + Idempotency-Key: reserve key atomically with the write, replay stored response, 422 on payload mismatch, TTL.

Missing-value rules

@PathVariable cannot be missing · @RequestParam/@RequestHeader/@CookieValue → 400 unless required=false/defaultValue · @RequestBody unreadable → 400 · two mappings, nothing distinguishing → startup Ambiguous mapping · trailing slash → 404 since 6.1.

Validation

starter-validation is separate from starter-web · @Valid on the body param, @Valid on nested fields, List<@Valid T> on elements · @Validated = groups + class-level param constraints, throws ConstraintViolationException (500 unless handled) · @NotNull < @NotEmpty < @NotBlank · custom: annotation + ConstraintValidator, null → true, cheap only · money: BigDecimal + @DecimalMin/@Digits.

Errors

One @RestControllerAdvice · resolver order: @ExceptionHandler (local beats global) → @ResponseStatus/ResponseStatusException → Spring defaults · unchecked ApiException + 4–5 subtypes, mapping in the advice not on the class · one shape: code, message, errors[], timestamp, path, traceId · all validation errors at once · ProblemDetail for new APIs (ResponseEntityExceptionHandler, spring.mvc.problemdetails.enabled) · whitelabel.enabled=false, include-stacktrace=never.

Filters & interceptors

Always chain.doFilter() or write a response · extend OncePerRequestFilter · @Component = /*; FilterRegistrationBean = patterns + order; both = runs twice · body is read-once → ContentCaching*Wrapper + copyBodyToResponse() · MDC/ThreadLocal cleared in finally · interceptor: register in addInterceptors; cleanup in afterCompletion, never postHandle; preHandle false must write the response.

Traps, one line each

DTO from @Controller → view error · own ObjectMapper bean → dates as numbers · entity on the wire → schema = API, lazy-init, recursion, leaks, mass assignment · uncapped size → DoS · Page count on hot tables → Slice/keyset · byte[] download → OOM · allowedOrigins("*") + credentials → startup fail · CORS with Security → http.cors() · Springfox on Boot 3 → dead, use springdoc · controller @Transactional → wrong layer · 200 body with an empty response → missing doFilter, missing copyBodyToResponse, or preHandle false.

Beyond the PDF

spring.threads.virtual.enabled=true (Java 21, Boot 3.2+) changes the cost of blocking, not the lifecycle · RestClient replaces RestTemplate; set timeouts, propagate the correlation id, circuit-break anything that moves money · @WebMvcTest + @MockitoBean (3.4+) tests the whole error contract without a server · Micrometer Tracing over hand-rolled correlation once there is more than one service.

If you can narrate the ten stages from memory, say which layer each concern belongs to, and describe one error shape with a trace id in it — you have Phase 3. Phase 4 goes back under the hood to AOP and the proxy mechanism that stage 7 depends on; Phase 5 takes on the data layer where most of the remaining performance decisions live.
